# Yuki's desktop shell (`yuki-ui`)

- **Alt+Shift** (`YUKI_HOTKEY`) toggles the overlay: dark glass, upper third of the primary screen. Enter submits, Shift+Enter adds a line, Esc or a click elsewhere hides it. Replies stack as cards, three at a time.
- **Two hotkey mechanisms** (`yuki/ui/hotkey.py`), because `RegisterHotKey` has no way to register a chord of modifiers on their own:
  - A combo that ends in a real key (`ctrl+alt+space`) is a `RegisterHotKey` registration on `HotkeyThread`'s message loop.
  - A modifier-only combo (`alt+shift`, two or more modifiers, no key) is watched by `ChordHookThread`: a `WH_KEYBOARD_LL` hook on its own thread. It fires once per press, as the last chord key comes back up, only if the held modifiers were exactly the chord and nothing else was typed meanwhile -- so Alt+Shift+Tab and Alt+Shift+P go where they always went. The hook observes and always calls `CallNextHookEx`; it never swallows a key. `HotkeyListener` owns both and re-emits one `pressed(action)`.
- **Alt+Shift is also Windows' input-language switch** when more than one keyboard layout is installed, so on such a machine the toggle also cycles the layout. Yuki does not suppress the system chord (a global hook that ate Alt+Shift would break every other program's use of it). Either switch layouts with the Win+Space picker and turn the Alt+Shift shortcut off in Settings > Time & language > Typing > Advanced keyboard settings, or set `YUKI_HOTKEY` (or `Settings.ui_hotkey`) to something else -- `ctrl+shift`, or any ordinary combo like `alt+space`.
- **Alt+Shift+X** (`YUKI_CANCEL_HOTKEY`) cancels whatever the task lane is doing, via `Agent.cancel()`.
- Tray icon: Show, model switch (sonnet/opus, both lanes), open the logs folder, Quit. One instance per session, held by a named mutex.
- **Task mode:** the first tool call of a task hides the overlay and puts a 360x56 status strip bottom-right — spinner plus one line built from the tool's own name and its most telling argument ("Launching app — spotify"). The strip never takes focus.
- **Nudge cards** (`yuki/ui/nudges.py`): memory sets `Local\YukiNudgeReady` when it writes a nudge; a watcher thread waits on it (plus a 60 s fallback look), fetches `pending_nudges()` and queues them. One card at a time, bottom-right like the strip, never focused, accent by kind (praise green, nudge amber, reminder blue), Reply and Dismiss, fading after 20 s. Queued (not shown) while the strip is up, the worker is busy, the overlay has a request in flight, a nudge reply is being written, or `SHQueryUserNotificationState` says full-screen / D3D / presentation / away. A card up when the strip arrives goes back to the head of the queue. Every outcome is `ack_nudge`ed once: `shown` (faded), `dismissed` (button, or Reply then closing the overlay unsent), `replied`, `snoozed`.
- **Reply to a nudge:** the overlay opens with the nudge as a context card; what the user types goes to `runtime.submit` prefixed with `[Replying to your nudge (kind: ...), sent HH:MM: "..." -- why you sent it: ...]`.
- **Tray, memory section:** Today's list (read-only panel of `todos(include_done=True)`: due soon, open, done today, with source and evidence), Quiet for 1 hour, Quiet until tomorrow (06:00), Nudges on (`snooze_nudges`). While quiet the status line reads `Memory: watching · quiet until 16:30`.
- **Questions:** `ask_user` dismisses the strip, brings the overlay back with the question as a card and a fresh input; the answer goes to `Agent.answer()`.
- **Endings:** the closing message lands wherever you are looking — as a card if the overlay is open, otherwise in the strip for four seconds. Errors are tinted red.
- **Two lanes** (`yuki/ui/runtime.py`), one `Agent` each, one `QThread` each, Qt signals only across the boundary:
  - `worker` — the full tool set, a FIFO queue of tasks, and sole ownership of the mouse and keyboard.
  - `front_desk` — used only while the worker is busy, built with `tool_names=LOOK_ONLY_TOOLS` and its own `extra_instructions`, on a backend whose action functions are stubbed out. It can look, read and answer, never touch.
- If the front desk reaches for a tool it does not have, that request needed hands: the runtime queues the original text for the worker and says so in a card. The signal is the refused tool call, never the wording of the reply.
- Every UI-side event (hotkey, overlay shown/hidden, submit, lane chosen, hand-off, queued, answer, cancel, model switch) is written through the existing `SessionLogger` as `type: "ui"` records in `logs/sessions/<id>.jsonl`; the two lanes keep their own `<id>-worker.jsonl` and `<id>-frontdesk.jsonl` transcripts.
