# Yuki's desktop shell (`yuki-ui`) and the Lattice design system

Two halves share one design: **the window** is HTML in WebView2 (its own process, 0 MB when closed), and **the ambient surfaces** (island, run card, cards, ask bar, toast, tray, first-run wizard) are native Qt, painted from the same tokens. The Qt window that predates Lattice (`docs/UI-window.md`) stays as the fallback engine. Evidence and build reports: `docs/research/revamp-2026-10-02/` (`25`, `28`, `31`, `32`); the mock the app must match is `docs/ui-mockups/revamp-2026-10/3-lattice/` (gitignored: it renders the user's real data).

## Lattice: the design (chosen 2 Oct 2026)

The user, 2 Oct ~23:45: "i really like the Lattice design better." Then, 3 Oct, after the refinement round: "the entire lattice is great."

- **Everything Yuki knows and does is drawn in dots.** In the window the background is the interface: panels are "clearings" the dots part around, with four crop marks as the only frame (no cards, no shadows, no glass). The field also draws page numerals, the week as dot columns and the day as a dot skyline. On the desktop, Yuki is the **island**: a small always-on-top window holding a 17×7 dot-matrix **face** and a bounded **halo** under it (560×170 px, an ellipse whose dots shrink toward the edge). Every live figure lives in that halo, never across the user's apps.
- **One colour, and it means live.** `live` mint (`#6FEBC4`) marks only something live: listening, the working head, rec, needs-you, Stop. Everything else is graphite and bone. Primary keys are lit bone, never coloured. **Errors are not red**: an error line is the brightest ink and is told by its words (2a flagged this; the user has not confirmed it, a red would be one token).
- **Signature motion: the field morph.** One canvas of dots per surface; cells ease toward a target level (k = 0.2 a frame) so states melt into each other. Page titles resolve out of `· : + * #` glyph noise into Doto letters; page figures sweep in column by column; the island morphs its size in 300 ms; the face keeps its expression history across states. The user (3 Oct ~07:25): "I am a real fan of this animation and the entire field UI", so the animations are the mock's own, not approximations.
- **Face expressions** (every one a waveform): idle, woke, listening, hearing, thinking, working, speaking, needs-you, quiet-in-call, game-quiet, voice-stopped, done-flash, handed, hidden-armed (plus `not-listening`, eyes shut, added by Yuki). Lit cells attack at 0.6 and release at 0.17 (a phosphor trail); a blink every 3.8-7 s only with the eyes open; off cells stay visible like a real matrix.

## The window engine (`window_engine = web | qt`)

`ui.json` (`%LOCALAPPDATA%\Yuki\ui.json`) key `window_engine`: **`web`** (default) is the Lattice HTML window, `python -m yuki.ui.web_window`; **`qt`** is the older native window, `python -m yuki.ui.window` (`docs/UI-window.md`; it keeps its round-2 layout with Lattice colours and Instrument Sans). `WindowHost.window_engine()` picks it on every tray click. It falls back to `qt` by itself when the WebView2 runtime is missing or fails to start (checked once per tray run). To get the old window back by hand: set `"window_engine": "qt"`.

## The WebView2 window: how it is built

- **Host.** `yuki/ui/webview2.py`: a thin ctypes host (a plain Win32 window plus the WebView2 controller made through the official `WebView2Loader.dll`, vtable slots read from the SDK's own metadata), not pywebview (pywebview would add ~47 MB and ~1 s before a window exists). No .NET, no Qt, no web server. The loader DLL comes from the pywebview package and is bundled by `packaging/yuki.spec`.
- **Locked down.** Files by **virtual-host mapping** (`https://app.yuki.example/` → `yuki/ui/web`, `https://fonts.yuki.example/` → `yuki/ui/fonts`; `.example` can never be a real site). Strict CSP: `default-src 'none'; script-src 'self'; style-src 'self'; font-src https://fonts.yuki.example; connect-src 'none'; frame-src 'none'; object-src 'none'; base-uri 'none'; form-action 'none'`. No inline script or style. Navigation off the app origin is cancelled (an http(s) link opens in the default browser), new windows and downloads are refused, every permission request is denied, no dev tools, context menu, zoom, autofill or host objects. The DOM is built with `createElement` / `textContent` (the one markup is the static icon table).
- **Data.** Data moves only over the message channel. The window **paints first from an encrypted snapshot** (`window-snapshot.bin`, the memory key unwrapped from its DPAPI file in ~50 ms, the web pages under their own format tag), then reads memory itself and talks to the tray over the window pipe (`yuki/ui/window_ipc.py`, 30 ops: `stop`, `steer`, `now`, `plan`, `card_feedback`, `activity`, `threads`, `people`, `workflows`, `workflow_edit`, `permissions_get`, `permissions_set`, `forget`, `offer`, `offer_undo`, `askbar` and the older ones). Page builders are in `yuki/ui/web_data.py` (no Qt). The page can do a closed list of named actions (28 when built, since extended), each a memory call, a settings write or a pipe op; tray-only ones say "Yuki isn't running" plainly when it isn't.
- **Chromium.** `--disable-gpu` by default (`DEFAULT_BROWSER_ARGS`): 69 MB less than the separate GPU process, the same first paint, and the window never opens a device on the GPU a game is using. `--in-process-gpu` (171 MB) is the fallback if software compositing janks on a visible window.
- **Measured** (Ryzen 7 2700, WebView2 154, 1440×900 at 100%, off-screen): first paint 1.0 s warm (1.19-1.22 s with a new profile), 167-171 MB private for the whole tree (host 39 MB, renderer 54, browser 38, GPU 17), **0 MB when closed**. Minimised or hidden: the page is hidden and WebView2's memory target drops to Low (working set 384 → 52 MB).

## The frameless window

The mock draws its own caption buttons, so the real window is frameless (`HostOptions.frameless`, default on; `yuki/ui/webview2.py`). `WM_NCCALCSIZE` removes the title bar but keeps the system's invisible resize borders and shadow; `WM_NCHITTEST` answers from `caption_hit()` (pure, tested): top edge and corners resize, the three caption buttons answer HTMINBUTTON / HTMAXBUTTON / HTCLOSE, the rest of the bar HTCAPTION, the page HTCLIENT. The page draws min / max / close with the mock's strokes, a drag bar (`app-region: drag`, with a JS fallback that asks the host to start the system's move loop) and a top resize strip, and reports their rectangles to the host. Minimise, maximise / restore and close act on release; a quick second press on the bar maximises.

Known limit: **snap layouts on hover over the maximise button cannot appear** (Windows hit-tests WebView2's child window there, never ours; only a composition-hosted WebView2 could hand the point back). Win+Z and dragging to a screen edge snap through the system's own frame. Not seen on a real visible window yet: dragging, double-click maximise, the system menu, resizing from the edges, DPI changes, multi-monitor.

## Motion and cost rules

| Rule | Why and measurement |
|---|---|
| One shared loop at 30 fps (33 ms); it runs only while a subscriber has more to draw | The face and the field each draw at 30 fps = 60 canvas redraws a second in a live state, as the mock measured |
| **Idle draws nothing**: 0 redraws, island 0% CPU; hidden = no timer at all | Window idle about 0.5-0.9% of one core with 0 redraws; island +5.8 MB private |
| No infinite CSS animation: toggle a class on a timer, or use the shared loop | An endless `animation` kept the compositor busy: 12.8% of one core idle, 0.95% with a class toggled every 800 ms. The only endless animations are on things that exist while something is live (the rec dot, a running step's spinner) |
| The idle face blinks on one shared 1 Hz tick, drawing the blink twice and no loop frames | +0.06% of one core |
| Covered by a full-screen app (a game, a presentation) and not in front: one still frame; back the moment it ends | 0.5% of one core, 0 redraws |
| Reduced motion (Settings, or Windows "Show animations" off): one static frame, no CSS animation, no blinks | The mock's own rule |
| A live state costs about 15% of one core in the window (listening 15.5, working 14.1, speaking 15.5) and 9-11% for the island listening or speaking, 5.6% working | In software compositing every frame costs about the same whatever its size; the only lever is frames per second, and the user chose the mock's motion over it (3 Oct). About 1% of this 16-thread CPU. |

## Shell behaviour

- **The ask bar shows the live chat thread** (phase 2): every typed or spoken message as a bubble, Yuki's replies streaming in, each response's steps in a fold; the same thread as the window's drawer. There is no glass setting and no light mode (removed 27 Sept); the look is Lattice, dark only, with the accent choice above.
- **Alt+Shift** (`YUKI_HOTKEY`) toggles the ask bar (`yuki/ui/overlay.py`, "the overlay"): Lattice, 780 px wide, 64 px from the top of the monitor in use. Enter submits, Shift+Enter adds a line, Esc or a click elsewhere hides it. Replies and recent coach nudges (last 12 h) stack as cards in time order, five at a time, in a scroll area capped at 55% of the screen height (mouse wheel anywhere on the panel, thin scrollbar); the input below it always stays on screen with the keyboard, and a new card or an arriving reply scrolls into view unless the user has scrolled up; typing within 30 min of an unanswered nudge sends it along as context (the model judges whether it is an answer).
- **Two hotkey mechanisms** (`yuki/ui/hotkey.py`), because `RegisterHotKey` has no way to register a chord of modifiers on their own:
  - A combo that ends in a real key (`ctrl+alt+space`) is a `RegisterHotKey` registration on `HotkeyThread`'s message loop.
  - A modifier-only combo (`alt+shift`, two or more modifiers, no key) is watched by `ChordHookThread`: a `WH_KEYBOARD_LL` hook on its own thread. It fires once per press, as the last chord key comes back up, only if the held modifiers were exactly the chord and nothing else was typed meanwhile -- so Alt+Shift+Tab and Alt+Shift+P go where they always went. The hook observes and always calls `CallNextHookEx`; it never swallows a key. `HotkeyListener` owns both and re-emits one `pressed(action)`.
- **Alt+Shift and the input-language switch:** Yuki's chord hook taps a mask key while the chord is held (the menu mask), so Alt+Shift no longer switches the input language on the same press; Win+Space still does. Any other combo can be set with `YUKI_HOTKEY` (or `Settings.ui_hotkey`): `ctrl+shift`, or an ordinary combo like `alt+space`.
- **Alt+Shift+X** (`YUKI_CANCEL_HOTKEY`) cancels whatever the task lane is doing, via `Agent.cancel()`.
- **Tray icon:** a left click opens the Yuki window (the engine chosen by `window_engine`, above; its own process). The icon carries the state (`yuki/ui/tray.py`), and its tooltip and hover card the call timer. The menu has Show (the ask bar), Open Yuki window, "Show what Yuki knows" / "Today's list" / "This week's review" / "Health check" (they open the web window's Me, Home, Work > Day and Activity pages; the four old tray panels are gone), pause and quiet-hours items, the voice items ("Voice (ctrl+alt+y, headphones)", "Listen for 'Yuki'", "Off for this call" during a call, "End tone when a conversation ends", microphone and speaker menus), model switch (sonnet/opus, both lanes), open the logs folder, Start with Windows, Quit. One instance per session, held by a named mutex.
- **Start with Windows** (`yuki/ui/startup.py`, checkable tray item, read afresh each time the menu opens): writes or removes the per-user value `HKCU\Software\Microsoft\Windows\CurrentVersion\Run\Yuki` = `"<project>\.venv\Scripts\pythonw.exe" -m yuki.ui.boot`. Not `yuki-ui.exe`: it is a console launcher (PE subsystem 3), so at logon it would open a terminal window whose closing kills Yuki. `yuki/ui/boot.py` sets the project folder as the working directory, points missing stdout/stderr at `nul`, waits for the taskbar (`Shell_TrayWnd`, polled for at most 120 s), then runs `yuki.ui.app.main`; the tray starts the memory service as always (`ensure_service`), so logon brings both up. A crash before the tray is up goes to `logs/ui-boot.log`. **Default on, once:** the first start of a tray with this code turns it on and writes `%LOCALAPPDATA%\Yuki\startup-default.json`; after that only the toggle changes it (off stays off; a value left pointing at an old environment is refreshed only while it is on). UI log: `startup_default` (`enabled` | `already_on` | `respected` | `refreshed` | `error`), `startup_toggle`. HKCU only, no admin.
- **At logon before the network is up:** nothing on the way to the tray needs it. The model warm-up retries quietly (30 s, 90 s, 240 s) when Bedrock cannot be reached at all; a request made meanwhile fails with its own error card. In the memory service every worker already retries on its own loop (journal, conversations, episodes, portrait, review, coach); a journal batch that cannot reach Bedrock no longer spends one of its captures' three attempts (`journal.unreachable`: the SDK's `APIConnectionError`).
- **Every run shows on the island from its first second** (2026-10-03; before, the strip came at the first tool call, 9.6 s into the one real "Do it", with no way to stop it): the moment any request starts (typed, spoken, anything) the island shows "Thinking…" and then the current step - built from the tool's own name and its most telling argument ("Launching app — spotify") -, the time so far and the step count ("12 s · step 3"), and a **Stop** key (clickable without taking focus; it calls `runtime.cancel(id)` for that request and reads "Stopping…" until the run ends). The first run of a session says the stop shortcut once ("Thinking… (Alt+Shift+X stops it)"). The worker's run keeps the island over a quick front-desk answer (whose final word shows briefly, then the worker's run comes back). **Task mode:** the worker's first tool call also hides the ask bar. The island never takes focus. (`yuki/ui/status.py` keeps the strip's interface; `IslandStrip` is the adapter that stands where it stood. Measured 3 Oct: the strip shown 4 ms after submit; Stop to cancel in 110 ms.)
- **Nudge cards** (`yuki/ui/nudges.py`, `lattice_cards.py`): memory sets `Local\YukiNudgeReady` when it writes a nudge; a watcher thread waits on it (plus a 60 s fallback look), fetches `pending_nudges()` and queues them. One card at a time, bottom-right, never focused, in the Lattice look (one colour; the kind is told by the header's mono label, no accent per kind), Reply and Dismiss, fading after 12 s plus 60 ms per character (at most 40 s; hovering pauses it). Queued (not shown) while a run is on the island, the worker is busy, the ask bar has a request in flight, a nudge reply is being written, or `SHQueryUserNotificationState` says full-screen / D3D / presentation / away. Every outcome is `ack_nudge`ed once: `shown` (faded), `dismissed` (button, or Reply then closing the ask bar unsent), `replied`, `snoozed`, and on cards with an offer `accepted` (its button) or `less` (Less of these; see Observation cards).
- **Question cards** (kind `question`, heading "Getting to know you"): memory asks something it would otherwise guess ("Who's Bro to you? You two talk about football plans on WhatsApp"). Buttons: **Answer** (an inline field on the card: memory's `answer_question`, ack `replied`; the agent can also save an answer from a request that carries the question's id), **Skip** (not now, not asked again) and **Don't ask** (never about this); both call `skip_question` and ack `dismissed`. Check-ins are question cards with the heading from their moment (Today, Your new thread, Following up, Tonight, Checking on you). Queued and shown like any nudge; one question card waits at a time.
- **Observation cards** (kind `notice`, `yuki.memory.presence`, 2026-09-29: "offers on cards only", Yuki never speaks first): a plain, specific notice - something keeps failing, a call's recap, a merge that leaves something open, the screen meeting something memory holds, a personal follow-up, a thread of work left open, a plan within a day. The heading says which (`NOTICE_TITLES` by the card's `trigger`: Noticed, After your call, Asking, From memory, Your work, Coming up). **No button ever starts an agent** (2026-10-03, `docs/research/revamp-2026-10-02/06-proactive-do-it.md`): a card may carry one **typed offer** (`offer` on the row: `do`, `label`, `steps`, `wont`, `expires_at`; `yuki.memory.offers`) - add to the list, show what Yuki holds, open again a page the user had, a draft to copy, or a suggestion for the ask bar. Then the card shows **Will:** (the offer's steps) and **Won't:** (a fixed line per kind) under the text, and its buttons are **Less of these**, **Not now** and one named for the action ("Add to list", "Show draft", "Edit in ask bar"); it lingers 6 s longer. Without an offer: Less of these, Dismiss, Reply. The welcome back may carry an offer too, and has Less of these as well. A free-text offer from before 3 Oct, or an offer past its 30 minutes, has no button.
  - **The action button** acks `accepted` and asks memory to check the offer again and run it **by code** (`offer_act`, off the GUI thread; no model call, no agent): the button reads "Running…" and the card shows the result in place - "Added to your list." or "Opened <page>." with **Undo** for ~8 s (`todo_add`: memory ends the to-do as a wrong capture; `bring_back`: the window that was in front comes back), the draft with **Copy** and Close (never sent or typed anywhere), what Yuki holds with Close, or why nothing ran ("This offer expired. Nothing ran.", "That's no longer there."). An `ask` offer closes the card and puts the suggestion in the ask bar, **unsent**; sent unchanged it is marked as Yuki's words (memory never stores it as the user's), changed it is the user's own request; stopped within a minute or closed unsent, it counts against that kind of offer. A second press does nothing. UI log `nudge_accepted`, `nudge_offer_result`, `nudge_offer_undo`, `nudge_offer_prefilled`.
  - **Not now** acks `dismissed`. **Less of these** acks `less`: feedback on that kind of card (memory halves that kind's day budget per press over 14 days; an offer that ran and was kept takes one back) and on that kind of offer (every Less, Not now, stop, Undo counts against it; a kind at -3 loses its button for a while); UI log `nudge_less`.
  - In the chat thread (the ask bar's and the window's), a card with an offer has its button (named for the action) beside Reply, and **Will/Won't** under the text (`ChatThreadView.do_nudge` -> overlay `do_nudge` / window `Actions.do_nudge` -> IPC `nudge_do` -> `NudgeController.accept_offer`; the Lattice window's Home uses the `offer` / `offer_undo` ops). The button says honestly where it stands (`nudge_state` `offer:<state>`): its label while it can run, then Running… / Done (with **Undo** in the ask bar and the window) / Undone / In the ask bar / Expired / No longer there; never "Done" at the press. A card that was dismissed, given Less of these, or whose offer expired loses the button in the history. A draft or what Yuki holds shows inside the card once it ran.
- **Questions:** `ask_user` puts the island in needs-you (Answer / Stop) and brings the ask bar back with the question as a card and a fresh input; the answer goes to `Agent.answer()`.
- **Endings:** the closing message lands wherever you are looking — as a card if the ask bar is open (the island then settles), otherwise in the island's done-flash for four seconds. A run the user stopped (Stop, or Alt+Shift+X) ends as "Stopped.", never as an error; real errors read in the brightest ink (there is no red in Lattice).
- **Two lanes** (`yuki/ui/runtime.py`), one `Agent` each, one `QThread` each, Qt signals only across the boundary:
  - `worker` — the full tool set, a FIFO queue of tasks, and sole ownership of the mouse and keyboard.
  - `front_desk` — used only while the worker is busy; since the revamp it is the **reader lane** (`yuki/agent/lanes.py`): read tools plus `hand_over`, on a backend whose action functions are stubbed out. It can look, read and answer, never touch.
- If the front desk reaches for a tool it does not have (or calls `hand_over`), that request needed hands: the runtime queues the original text for the worker and says so in a card. The signal is the refused tool call, never the wording of the reply. `runtime.submit` also carries the voice's `user_words` (for the authorization judge) and the request `pack`.
- Every UI-side event (hotkey, ask bar shown/hidden, submit, lane chosen, hand-off, queued, answer, cancel, model switch) is written through the existing `SessionLogger` as `type: "ui"` records in `logs/sessions/<id>.jsonl`; the two lanes keep their own `<id>-worker.jsonl` and `<id>-frontdesk.jsonl` transcripts.
- **Voice** (`docs/VOICE.md`): tray items above, hotkey **Ctrl+Alt+Y** (`YUKI_VOICE_HOTKEY`), and the island carries the voice states (Listening, Hearing you, Thinking, Speaking, Working, errors, "Say 'Yuki' to talk again" after a conversation ends by itself). Off until turned on; questions from voice requests reach the island's needs-you state without taking focus; Alt+Shift+X also cuts Yuki's speech.
