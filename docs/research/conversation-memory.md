# Conversation memory for Yuki — 2026 research and recommended design

Yuki already has ambient memory (encrypted SQLite journal of Haiku-extracted dated facts, 384‑d local embeddings with vector+keyword recall, hourly episodes, a nightly Sonnet-written bi-temporal user portrait, corrections, and know-how). What's missing is memory *of the conversations themselves*: rules the user sets mid-chat, tasks handed off, running jokes, the assistant's own commitments, and continuity across app restarts. Below is what the field does in 2026, then a concrete design that reuses what Yuki has.

## 1. Letta (MemGPT)

Letta's model (evolved from the 2023 MemGPT paper) splits memory into three tiers: **core memory** (small, always-in-context blocks — persona + human — that the agent edits with function calls), **recall memory** (the full raw conversation log, outside context, searchable by the agent on demand), and **archival memory** (a vector store for facts the agent explicitly writes for long-term keeping). The defining trait is *self-editing*: the LLM itself calls `core_memory_append`, `archival_memory_insert`, `conversation_search`, etc. rather than a fixed pipeline deciding what's important.

The newer piece is **sleep-time agents**: a second agent that runs during idle time (not on the user's critical path) to consolidate fragmented memories into coherent entries, deduplicate/reorganize memory blocks, and prune stale ones — inspired directly by biological sleep consolidation. This decouples "remembering well" from "responding fast." Letta also does automatic message-history compaction when the context fills up.

User reports: self-editing gives flexibility but is chatty (extra tool calls burn tokens/latency) and quality depends on how disciplined the model is about writing to memory; sleep-time agents fix the latency cost but add operational complexity (a second scheduled process, consolidation prompts that must avoid overwriting nuance).
[Letta docs](https://docs.letta.com/guides/legacy/memgpt_agents_legacy) · [Agent Memory blog](https://www.letta.com/blog/agent-memory/) · [Sleep-time Compute](https://www.letta.com/blog/sleep-time-compute/) · [sleep-time-compute paper/code](https://github.com/letta-ai/sleep-time-compute) · [forum best-practices thread](https://forum.letta.com/t/sleeptime-agents-for-memory-consolidation-best-practices-guide/154)

## 2. Mem0 / Mem0g

Mem0 treats memory as a pipeline, not agent self-editing: after each turn, an LLM (extraction step) pulls candidate atomic facts from the message pair, then a second LLM call compares each candidate against existing similar memories and decides **ADD / UPDATE / DELETE / NOOP**. This keeps the store small and non-redundant instead of growing forever. Mem0g extends this to a graph: entities and relation triplets are extracted, contradictory/updated facts invalidate older edges (temporal awareness), and retrieval can walk relations, not just vector-search flat facts.

Numbers matter here: Mem0 scored **91.6% on LoCoMo** (a +20.2 pt jump over the prior best) and **93.4% on LongMemEval** (+25.6 pt), while using **under ~7K tokens per retrieval** versus 25K+ for full-context baselines — roughly **90%+ token reduction** and **91% p95 latency reduction** (1.44s vs 17.12s) against a "stuff everything in context" baseline. Cost stayed flat (~$0.0007–0.0015/query) while long-context cost ballooned to ~$0.09/query at 300 conversations (up to 95x savings at scale).
[Mem0 paper](https://arxiv.org/pdf/2504.19413) · [Mem0 research/benchmarks](https://mem0.ai/research) · [breakdown](https://memo.d.foundation/breakdown/mem0) · [token-efficient algorithm](https://mem0.ai/blog/mem0-the-token-efficient-memory-algorithm)

## 3. Zep / Graphiti

Zep's Graphiti engine builds a **temporal knowledge graph** with three layers: an *episode subgraph* (raw messages/events, each timestamped), a *semantic entity/fact subgraph* (entities and relations extracted from episodes, each edge carrying **bi-temporal validity** — when a fact became true and when it stopped being true in the world, separate from when it was recorded), and *community summaries* (cluster-level abstractions via label propagation, i.e. rolled-up themes). When a new fact contradicts an old one, Graphiti doesn't delete the old edge — it sets its `t_invalid` to the new fact's `t_valid`, preserving history instead of silently overwriting it (important for "what did I used to think/say" questions). Retrieval fuses cosine similarity + BM25 + graph traversal with reranking (RRF/MMR/cross-encoder). Zep reports state-of-the-art accuracy on memory benchmarks at lower token cost and latency than full-context or naive-RAG baselines.
[Zep paper](https://arxiv.org/abs/2501.13956) · [Graphiti docs](https://help.getzep.com/graphiti/getting-started/overview) · [temporal KG explainer](https://www.getzep.com/ai-agents/temporal-knowledge-graph/)

## 4. Other frameworks and benchmarks

- **LangMem** — a memory layer built into LangGraph; stores memories as JSON documents in a namespaced store, retrieved via filters. Mainly working-memory compression (summarize long histories into actionable notes), not a deep graph. Good fit only if you're already on LangGraph.
- **A-Mem** — Zettelkasten-inspired: each memory is a "note" that gets dynamically linked to related notes, so retrieval follows an evolving link structure rather than flat similarity.
- **MemoryOS** — frames memory as an OS: explicit storage/retrieval/update modules across memory "levels" (short/mid/long-term), aimed at persistent personalization.
- **Cognee** — a graph-native memory control plane combining relational + vector + graph storage in one engine; aimed at many agents sharing one knowledge graph from many data sources (heavier than a single-user assistant needs).
- **Benchmarks**: **LoCoMo** (long conversational memory QA) and **LongMemEval** (now iterating to v2, "toward experienced colleagues") are the two standard yardsticks; 2025–2026 spawned many more (MemBench, MemoryAgentBench, MemOps, UTILMEM, MemTrace) probing specific failure modes — e.g. MemTrace and MemOps show final-answer accuracy hides whether the *lifecycle* operation (add/update/delete/forget) was actually correct, which is directly relevant to "don't let corrections get silently un-done."
[Cognee comparison](https://cognee.ai/blog/guides/best-ai-memory-layers-for-ai-agents-in-2026-comparison) · [LongMemEval-V2](https://arxiv.org/html/2605.12493v1) · [MemOps](https://arxiv.org/pdf/2607.12893) · [MemTrace](https://arxiv.org/pdf/2606.17328)

## 5. Anthropic context engineering + first-party memory

Anthropic's public guidance (Sept 2025 "Effective context engineering," updated through 2026) frames this as finding "the smallest set of high-signal tokens" per turn, via a **hybrid** of upfront injection (fast, small, curated) and just-in-time retrieval (tools that fetch on demand, avoiding stale/duplicated indexes). Three concrete mechanisms now ship on the API:

- **Memory tool** (`memory_20250818`): a client-side, file-based tool (`view`/`create`/`str_replace`/`insert`/`delete`/`rename` over a sandboxed `/memories` directory). Claude checks memory *before* starting a task and writes what it learns as it works — genuinely "just-in-time" retrieval instead of front-loading. It is explicitly billed as surviving compaction/context resets: "assume interruption... any progress not recorded in your memory directory is lost." Your app owns storage/security (path-traversal protection, size caps, expiry of stale files).
- **Compaction**: server-side, triggered automatically as context nears the window limit; an LLM writes a holistic summary preserving "architectural decisions, unresolved issues, implementation details" while discarding redundant tool output. Anthropic recommends triggering this *aggressively, well before* the window is full, to stay ahead of context rot.
- **Context editing**: client-directed clearing of specific stale tool results (lighter-weight than full compaction).

Anthropic's own recommended combination for long-running agents: use compaction to keep the *active* window small automatically, and the memory tool to persist the specific facts that must survive summarization. **Context rot** — the (Chroma-coined, now widely used) finding that all 18 tested frontier models degrade in retrieval/reasoning accuracy as input length grows, even well under the nominal context limit, with the worst loss for information placed in the middle of a long context — is the reason not to just keep dumping everything into one giant always-attached prompt.

Separately, prompt caching (cache reads ~10% of base input cost) makes it cheap to keep a stable "preamble" block (persona + rules + portrait) attached every turn as long as it doesn't change every message — put the volatile bits (today's episodes, latest recall hits) *after* the cached block, not inside it, so the cache still hits.
[Effective context engineering](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents) · [Memory tool docs](https://platform.claude.com/docs/en/agents-and-tools/tool-use/memory-tool) · [Context rot / Chroma](https://www.trychroma.com/research/context-rot)

## 6. ChatGPT memory & persona/relationship continuity

OpenAI's ChatGPT memory has two parts: **saved memories** (discrete user-stated or model-inferred facts, edited like custom instructions) and **reference chat history** (a background synthesis of *patterns* across past chats, not raw recall). In June 2026 OpenAI replaced the old summarizer with **"Dreaming"**: an asynchronous process that reads across many past conversations and maintains one synthesized memory state, injected at the start of each new chat — explicitly built to fight staleness/incorrectness at multi-year, hundreds-of-millions-of-users scale. This is architecturally close to Letta's sleep-time agent and to what a nightly Sonnet portrait job already does for Yuki, just applied to *conversation history* as well as ambient activity.

On persona/relationship continuity specifically, the research consensus (ZifaMem, AutoPersonas, and companion-AI UX studies) is: continuity requires an explicit, separately-maintained **consolidated user-model + relationship state** (name/nickname rules, tone preferences, running jokes, commitments) distinct from raw episodic memory, because users judge "does this feel like it knows me" on that consolidated layer, not on perfect recall of every line. The main safety finding: assistants must not surface sensitive disclosures out of context, and users need visible control (view/edit/delete) over what's remembered — parallel to Yuki's existing "corrections" mechanism.
[OpenAI memory announcement](https://openai.com/index/memory-and-new-controls-for-chatgpt/) · [Memory FAQ](https://help.openai.com/en/articles/8590148-memory-faq) · [ZifaMem](https://arxiv.org/pdf/2607.17564)

## Comparison table

| Option | Core mechanism | Fit for Yuki | Cost / complexity |
|---|---|---|---|
| Letta-style core/recall/archival + sleep-time agent | LLM self-edits 3 memory tiers; background agent consolidates | Good conceptual model, but self-editing means extra tool round-trips per turn; sleep-time agent = another scheduled job | Medium-high: needs its own agent loop + storage tiers |
| Mem0 (ADD/UPDATE/DELETE) | Extract facts per turn → LLM diff against existing memory → single-op write | **Best structural match** — Yuki's journal already does dated-fact extraction; Mem0's diff step is the missing "don't duplicate/contradict" logic | Low-medium: 1–2 small Haiku calls per turn, small vector index (already have one) |
| Zep/Graphiti (temporal KG) | Episodic→semantic graph, bi-temporal fact invalidation | Most rigorous "what changed when" model; overkill to build a graph DB from scratch for one user | High: needs a graph store, entity resolution, more infra than SQLite+embeddings |
| LangMem | JSON memories in LangGraph store | No LangGraph in Yuki's stack | N/A — wrong ecosystem |
| Cognee | Unified graph/vector/relational control plane, multi-agent | Built for many agents/many sources; single-user assistant doesn't need it | High, not justified |
| Anthropic memory tool + compaction | File-based `/memories`, just-in-time reads, server compaction | Directly usable pattern for the "always-attached vs retrieved" split; compaction handles in-session overflow | Low: mostly wiring, cheap with caching |
| ChatGPT "Dreaming" style synthesis | Async cross-conversation summarizer injected each new chat | Same shape as Yuki's nightly portrait job, extended to include conversation history | Low: reuse existing nightly Sonnet job |

## Recommended design for Yuki

**Store, per conversation turn** (cheap, Haiku): after each user+assistant exchange, run one small extraction call (same pattern as the existing journal extractor) that emits, only when present: (a) explicit **rules/preferences the user set about how to talk** ("call me babe", tone, formatting), (b) **tasks/commitments** — what the user asked for and what Yuki promised, with status (open/done), (c) **notable facts** worth folding into the portrait pipeline (reuse existing journal path — don't build a parallel fact store), (d) a short **turn summary** (1–2 lines) for the episode/session log. Write these as rows in the existing encrypted SQLite (a new `conversation_facts`/`commitments` table, embedded with the existing 384-d model) rather than a new store — this is the Mem0 ADD/UPDATE/DELETE pattern, reusing infrastructure Yuki already has instead of Letta's file tiers or Zep's graph.

**Diff, don't just append**: before writing, do a cheap ADD/UPDATE/DELETE check against existing rows with the same subject (vector nearest-neighbor + keyword match, which Yuki already supports) — this is Mem0's single most load-bearing idea, and it directly prevents "context pollution" (stale/contradicted facts sitting around forever). When a new fact contradicts an old one, don't delete — mark the old one invalidated with a timestamp (Zep's bi-temporal trick) so Yuki can still answer "what did I used to think."

**When to summarize/consolidate**: three tiers, matching what already exists —
1. *End of session* (app close / long idle): cheap Haiku pass writes a session summary + updates commitment statuses. This is the "episode" mechanism already running hourly; conversations should feed the same table with a `session` grain.
2. *Nightly* (already scheduled): fold the day's conversation facts + commitments into the existing Sonnet-written portrait job, adding a "relationship/rules" section alongside work/interests/people/routines/preferences — this is exactly the Letta sleep-time-agent / ChatGPT "Dreaming" pattern, but it's a job Yuki already runs, just needs a wider input (conversation turns + episodes, not just ambient capture) and one new output section.
3. *On-demand recall*: a `recall_conversations` tool (mirroring the existing embeddings recall tool) that the agent calls when a user references something not in the always-attached context ("what did I ask you last week about X").

**Always-attached vs retrieved (token budget)**: keep the always-attached block small and cache-stable — persona/system prompt + the nightly portrait (as now) + a new **~150–300 token "active commitments & rules" block** (open tasks, standing rules like nicknames, current running jokes) pulled fresh each turn since it's small and changes daily. Everything else — full conversation history, old session summaries, superseded facts — stays out of the prompt and is fetched only via the `recall` tool, exactly the Anthropic memory-tool philosophy ("just-in-time," not front-loaded) and Mem0's measured result that <10% of full-context tokens gets equivalent-or-better accuracy. Put the volatile commitments block *after* the cached persona/portrait block in the prompt so prompt caching still hits on the stable prefix.

**Enforcing commitments and user-set rules**: give them first-class status, not just "a fact somewhere." Store each rule/commitment with a status field (active/fulfilled/expired/revoked) and surface *active* ones verbatim in the always-attached block — this is stronger than hoping the retrieval step finds them, and matches the finding that rule-following commitments need explicit lifecycle tracking, not just recall accuracy (MemOps' point: it's not enough to retrieve, the add/update/delete lifecycle itself must be verified). Corrections the user already makes should be able to target these rows directly ("no, stop calling me babe" → sets that row to revoked), reusing Yuki's existing corrections mechanism instead of inventing a new one.

**Keep it cheap**: Haiku for all per-turn extraction/diff calls (small, structured-output tasks — exactly Mem0's and Yuki's existing journal pattern); Sonnet only for the nightly consolidation (as now); prompt caching on the persona+portrait prefix; cap conversation-fact table size the way the memory-tool docs recommend for files (periodic pruning of anything unaccessed and superseded for N days, keep invalidated-not-deleted for provenance). This avoids Zep/Cognee-level graph infrastructure while capturing their core wins (temporal invalidation, explicit lifecycle) inside SQLite + embeddings Yuki already runs.
