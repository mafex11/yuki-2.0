# Yuki voice — design contract (v3.19, as built)

Goal: talk to Yuki the way you talk to a person sitting next to you. You say "Yuki", it answers within a couple of seconds, you can cut it off, it keeps talking with you while it works on your PC, tells you what it is really doing, and tells you what it found when the conversation is quiet. It never makes things up. Nothing gets slower on the PC side: the brain keeps its full thinking.

**Status (2026-09-25, v3).** v2 (talking loop, brain hand-off, follow-ups, cancel, wake word) plus the v3 behaviour set from gradient-bang's design (docs/research/voice-parallel.md): the talker decides every turn with commitment discipline and a structured hand-off (`request` + `context`), a grounding memory lookup on every turn, spoken progress from the thinker's real tool calls, "how's it going?" answered by an isolated one-shot over the task's action log, a narrator gate (no talking over the user, settle, cooldown, stale results folded silently), results condensed in code, follow-ups that restart a finishing task quietly, a Bedrock keep-alive that removed the unexplained latency, less RAM, fewer false wakes, the wake word on by default and a tray setting for the voice id. Every test ran from audio files into WAV files with real Deepgram, real Bedrock and real TTS (ElevenLabs and Aura); nothing opened the microphone or played on the speakers (ARCHITECTURE.md rule 7). **The first live test is the user's** (§24). Numbers marked *measured* come from `scripts/voice_*.py` runs on this PC.

All rules in `docs/ARCHITECTURE.md` apply.

**v3.1 (2026-09-25, after the first live conversation).** Measured offline (clips replaying the live session, file transport, real Flux/Haiku/Sonnet, a stand-in memory service; `scripts/voice_scenarios.py live925 --serve-embedder --grounding on`):

- **One embedder on the PC** (`yuki/memory/embed_ipc.py`): the memory service serves its embedder on a local, user-only named pipe (DACL = this user, remote clients refused, HMAC challenge both ways with a key derived from memory's DPAPI data key; JSON requests, raw float32 replies). `MemoryClient` embeds through it; only when no service answers does a local one load, in the background. Every caller passes a wait bound: know-how 0.6 s, the grounding lookup 0.4 s, then it goes without (a busy service is never a reason to load a second copy). Measured: know-how lookup 10–15 ms (was 2.3–3.9 s cold), tray +8 MB instead of +570 MB; a conversation with grounding **~210 MB** (was ~800). `voice_grounding` is on again; it switches itself off for a conversation when no service embedder answers.
- **Brain for voice:** `Settings.voice_brain_effort` ("low") for spoken requests only (`Agent.run(effort=)`, chosen by the job's source, never its words). Every action tool takes an optional `finishes_with`: the brain's own mark that the call completes the request; the request ends the moment it succeeds, with no second model call (in 159 real requests Sonnet never sent `done` alongside an action). "Minimize Discord": 8–9 s → 3.9–4.9 s, one call (4 of 5 runs); "time in Tokyo": 7.2 s → 4.8–5.1 s.
- **Mouth:** words before every hand-off, and a required `say_first` spoken by the bridge when a reply had none (the live "On it" came 11 s late: the reply had no text; text probe 0/5 → 5/5 with words first). Acknowledgements get an acknowledgement, never the last answer again; the Now line is "for when they ask". Rule changes, corrections and life facts go over quietly as `intent: remember` (the outcome is folded in, not spoken; the mouth's rules layer is re-read at once). Pipecat's "a result is owed whatever the conversation moved on to" paragraph is replaced (the gate decides). Feeling goes into the words (no tags).
- **Narrator:** a result or a question is said as soon as the user is not talking and nothing is owed: a 0.3 s gap after Yuki's speech (`voice_final_gap_s`) and no settle unless another task is running. Progress lines keep the cooldown and settle.
- **First turn:** the warm-up carries the real system layers and tools, so the first turn reads the cache (first-turn TTFT median 1,031 vs 1,186 ms over 4 pairs); botocore's Bedrock stream model and anyio's lazy maps are loaded off the loop (they stalled the loop 0.4–3 s inside the first reply). A watchdog records where the loop is on any stall ≥ 0.3 s (`loop_lag.where`, content-free).
- **Timing log:** end of speech is judged against the room's floor (a Bluetooth headset never reached the fixed −42 dBFS, so every live turn was blank), with speech recognition's last new word as the fallback (`eos_source`); new `eos_to_first_token_ms`; columns in pipeline order; each mouth run is its own row.
- **TTS:** optional ElevenLabs voice settings (`voice_tts_speed`, `_stability`, `_similarity_boost`, `_style`, `_speaker_boost`, or the same keys in `voice.json`), unset by default. A voice the account may not use (402 `paid_plan_required`, unknown id) falls back to the default ElevenLabs voice for that conversation with a note in the pill.

**v3.2 (2026-09-25, after the second live test: "on it… 4-5 s later it starts", "what's up?" after every job, 8-10 s for a scroll).** Measured offline (`scripts/voice_scenarios.py hands`, clips `h_*`, file transport, real Flux/Haiku/Sonnet, the hands stub desktop; before = the v3.1 code on the same script):

- **The talker has hands** (§5.6): one-step desktop tools it calls in the same reply as its words (a key in a window, media/volume keys, scroll, focus/minimize/maximize/restore/close, open a URL or an app), on a desktop summary attached to every call. "Minimize Discord": action 9.6 s → 2.4 s after end of speech, "done" audio 11.2 s → 3.7 s.
- **"What's up?" found:** Pipecat stores a reply's words *after* the tool call they announced, so a result that settled in place sat before them; the adapter then padded the request with a user message "." (no prefill on the `global.` id). The mouth answered the "." ("What's up?", "I'm here. What's up?", and offline it read a `<thinking>` about the clock aloud). `pipeline.chronological` puts each reply's words back before its calls: the result is the newest thing. Plus: `stay_quiet` (a turn with nothing new can be silent), "never write your reasoning", `check_progress` refused when the user did not ask (§5.2), progress only after 8 s of Yuki's silence (§6.4).
- **Thinker for voice** (§7): thinking off and a slim memory block for spoken requests; first model call median 4.9 → 3.0 s (6 tasks, stub desk). Haiku 4.5 (1.6 s) was faster but claimed things it had not checked; it stays a setting.
- **open_url** returns once the page is at the address (the 1.9 s content wait is gone), the Start-menu list (1-3.4 s cold) is read at start-up, and `launch_app` logs `timings_ms` per stage.
- **Devices:** tray **Microphone ▸ / Speaker ▸** (§12).

**v3.3 (2026-09-25, after the third live test, 18:54-18:57: "it says the whole sentence and only then scrolls", "done" three times for things that did not happen, the thinker clicking the wrong "new" tab, one more "What's up?").** Measured offline (`scripts/voice_scenarios.py hands3`, clips `c_*`, file transport, real Flux/Haiku/Sonnet, the `BrowserDesk` stub; before = the v3.2 code on the same script and stub, §23):

- **Instant hands act at once** (§5.6): `press_keys`, `media_key`, `scroll`, `window` and the new `tab` are called with no words before them, so the action runs the moment the tool call is complete; what is heard is the hand's done line, said by code from its verified report (no second model call). `open_url` / `open_app` (seconds) and hand-offs keep a few words first.
- **"Done" only from a verified effect:** the done line needs the hand's report to say `verified`: a window's state, the tab selected (UIA `SelectionItem`), the scroll position moved, the media session's status or the output volume changed, the page at the address *and* titled. Otherwise the mouth says honestly what the report shows and hands it to the thinker.
- **Scroll acts on the page, not the cursor** (`yuki/actions/scrolling.py`, used by the brain's `scroll` too): UIA `ScrollPattern` on the scrollable element at the point (or its nearest scrollable ancestor, else the window's largest scrollable area), `SetScrollPercent` by a screenful per 10 notches, cursor untouched; only without a pattern the wheel at the point with the cursor put back. Read back: `ok` False when it did not move or is at the end.
- **Tabs are not windows:** the desktop block lists the foreground window's tabs (`yuki/perception/tabs.py`: TabItems outside any page, read ahead when the user starts talking), and the `tab` hand selects one (`yuki/actions/tabs.py`: `SelectionItem.Select`, else Invoke, else the default action; verified by `IsSelected`; refused when the list changed).
- **What was done is shared:** every hand action and every thinker desktop action, with what was verified, goes into the conversation's action log (`hands.ActionLog`, RAM only): its last lines are in the mouth's desktop block and handed to the thinker with every voice request; an opened page records its tab ("tab 4 of 4 in window …, "YouTube"").
- **"What's up?" found again:** not an empty STT final (Pipecat drops those): job 5's result arrived after the mouth had spoken and called `stay_quiet` on job 4's result; Pipecat settles an async result in place unless a user or developer message follows its placeholder, so it went into the middle of the context and the newest thing the mouth saw was its own `stay_quiet` (the cache-read drop 9,401 → 7,813 at that turn is the rewrite). `pipeline.settle_only_when_newest`: a result settles in place only when its placeholder is the newest message, else it is appended. Results also say which request they answer (`for_request`; the mouth had said job 4's result as job 5's). Pipecat's context summary no longer counts as "what the user said" to the thinker, and summaries happen by size only (8k tokens), not every 20 messages.
- **Repeats:** "again", "more" of a hand's step is that hand again (prompt, worked example).

**v3.4 (2026-09-26: "say Yuki anytime").** From the logs: on one day the user was in voice calls for over 12 hours and the wake word was paused the whole time (`call_on`); on 26 Sept at 18:20 "Yuki" was heard 5 times and every conversation stopped at once with "Voice needs headphones for now" (the output was the M-Audio speakers), and the user saw nothing. Measured offline (unit tests on a simulated room; `scripts/voice_session_offline.py`: the real `VoiceSession` from the wake word on, a pretend mic and speaker joined by a pretend room, real Flux, Haiku and Aura):

- **Speakers work** (§11): WebRTC's echo canceller (AEC3, livekit 1.1.20) with Yuki's own playback as the reference, chosen by the output's form factor; half duplex when it cannot load; full duplex on headphones. End to end with Yuki's reply echoing back at -8 dB: canceller and half duplex, 1 user turn and 1 reply, nothing of hers transcribed; no guard (the control), 11 self-replies in 60 s. Barge-in stays on with the canceller.
- **Never silent** (§16): a failed start or an error plays a short tone (once a minute per reason) and the pill shows the reason for 8 s, wide enough to read, and no longer vanishes when voice goes back to listening for the name.
- **The name works in calls** (§25): `voice_wake_during_calls` on; a conversation in a call is in call mode: the mouth decides from its own judgement whether each utterance was for Yuki or for the people on the call (a call layer with worked examples, `stay_quiet` for the call), and the conversation ends 10 s after the last exchange with Yuki. Talk to the call is not kept in memory and never reaches the thinker.
- **Wake reliability** (§22, §26): everything said from the name on is kept (12 s backlog, handed to speech recognition with no block lost or doubled, long silences squeezed out: Flux works through a burst at only ~1.25x real time); the wake-started replay was broken since v3 (frames pushed before Pipecat's input queue existed) and is fixed; "Listening" and a soft chime 2-91 ms after the spotter fires; the spotter restarts on each sound episode; the mic recovers from device changes and sleep (PortAudio's device list is re-read, a failed reopen is retried).
- **The tray's Speaker is really used** (§12): live 26 Sept the tray chose "Headphones (<model>)", the headphone check read them, but the voice played on the M-Audio speakers: PortAudio's device list predated the headphones and the name fell back to its default in silence. The output is now opened by name, the list re-read when the name is missing, the echo mode decided on the device that really opened, a miss said in the pill, and a change in the tray moves a running conversation's output at once.
- **Session flow** (§5, §15): a back-and-forth earns a longer quiet window (20 s, +8 s per further exchange, up to 45 s); a wake heard while a conversation is closing starts the next one right after it.

**v3.5 (2026-09-26 night, after the live sessions of 20:52-21:05 and 21:22-21:31).** Evidence: `conversation_turns` (read-only copy), `voice-20260926.jsonl`, `voice_turns.csv`, the worker log. Measured offline only (§27): `voice_scenarios.py latency926 | tabs926`, `voice_session_offline.py latency [--prewarm] [--one-breath]`, `voice_keyterms.py`, unit tests `tests/test_voice_v35.py` (23).

- **No blind hands** (§5.6): the talker has no keyboard (`press_keys` removed: live it pressed Ctrl+W on whatever tab showed, closed the video 3 times and Gmail once, "undid" with Ctrl+Shift+T into the wrong tabs). A tab is closed only through `tab(action=close)`, by the identity (UIA RuntimeId) of the tab the talker was shown, verified gone, with `named` (the user's words naming each); a closed tab comes back only through `tab(action=reopen, expect=<title>)`, the browser's own reopen verified by title. After a window hand whose report does not show its effect, the talker's window hands stay still until the user speaks. While a thinker job runs on the worker, window hands are refused (one actor); sound hands still work.
- **One app's volume** (`yuki/actions/app_volume.py`): Core Audio `ISimpleAudioVolume` on the app's audio sessions, read back, no focus change, no window touched (a game stays in front); the talker's `app_volume` hand, the thinker's `app_volume` tool, and an "app volumes" line in the desktop block. `media_key` says it is the SYSTEM volume. The thinker also has `hover` (`yuki/actions/hover.py`: the pointer onto an element, reporting what appeared, e.g. YouTube's volume slider).
- **Who is addressed, every conversation** (§5.1): the mouth decides whether each utterance was for Yuki (dictation to another app, talk to someone else: `stay_quiet` alone, no words); `end_conversation` ends the session on "you can turn off the voice" (never a rule); a stay_quiet in a run a result or question started is refused once (a result is always said).
- **Pill** (§12): "Working on it" only while a job is queued or running; a reply with no words, a folded result or a cancelled job returns it to "Listening" (live it stayed "Working on it" for 60 s after a remember job).
- **Latency** (§9, §14): tool-first hand-offs (`say_first` first in the call, spoken the moment its string is complete in the stream); eager end of turn **on** (0.4) after fixing its duplicate replies (a race in Pipecat's eager stop strategy, `pipeline.one_stop_per_turn`) and holding a speculative reply's tool calls until the turn is confirmed.
- **Wake** (§26, §27): background prewarm after start-up (imports, stream decoders, TTS check, TLS, DNS, mixer COM, TTS quota); the voiced level no longer counts a noisy interface's floor as speech (the replay after a wake is squeezed again).
- **Recognition** (§9): keyterms from memory (`MemoryClient.speech_names`: the right names of the user's corrections first, never a misheard form, then the portrait's people and names; `yuki/voice/keyterms.py`). The mouth's core carries the universal defaults (short and on point, no dashes or parentheses, say it once, "sent" without reading back, send only on a plain instruction, to-dos only when asked). **Learning**: `tell_yuki(corrects=…)` carries the user's correction to the thinker (`[Correction from the user: …]`). The grounding lookup uses fast memory (`MemoryClient.relevant`) plus the nearest know-how; the profile layer carries Yuki's persona.
- **TTS quota**: the free ElevenLabs tier ran out (10,000/10,000 characters, resets ~26 Oct): every reply then had no audio and Pipecat gave the TTS up after three. Preflight now reads the quota and falls back to Aura below 400 characters.
- **Chat UI** (§12): `VoiceSession.user_utterance`, `assistant_speech`, `hand_step`, `job_event`, `chat_event`.
- **Ask back when recognition was unsure** (§28): Flux's per-word confidence and heard words close to a known name become a Speech recognition line for the mouth; it asks a short question before anything that changes things, and a window hand or hand-off called together with words on such a turn is held until the answer. **Model failover** for the mouth (retry, then the `model_fallbacks` chain), and `call_mode` in the narrator's state.

- **Narrator** (§6.3, §6.4): an action is never a progress line (it takes effect long before a line could be said); a waiting line is dropped once the job moves to another step; nothing is released while words are on their way to the voice (`speech_pending`: live the result was handed over in that gap and said right after the stale step); the thinker's own finishing line (`finishes_with`, its action succeeded) is said as it is, once, by code, with no mouth run (live the mouth padded "Bluetooth settings are open." with advice).

**v3.7 (2026-09-27 morning: "make voice replies faster", "fix the wake word missing 'Yuki, do X' in one breath").** Measured offline (`voice_scenarios.py parallel927`, two runs each, real Flux / Haiku / Sonnet / Aura; probes in the build's scratchpad).

- **Where the ~2.3-2.5 s goes** (end of speech -> first audio): Flux's eager end of turn 0.3-0.6 s, the mouth's time to first content 1.25-1.45 s (p50 1.39 s), first text -> TTS 0.15-0.4 s, Aura's first byte 0.30 s. Probed: Haiku 4.5 time to first token with the real 12.2k-token prompt 1.30-1.48 s on `global.` from ap-south-1 and 1.05-1.39 s on `us.` from us-east-1 across runs (no stable winner; us-west-2 1.72 s); a bare call 0.89 s; the prompt costs ~30 ms per 1k cached tokens (5.6k 0.99 s, 22.4k 1.51 s). Eager at 0.3 instead of 0.4 fired no earlier (0.34-0.79 s) and lost a reply. **The 1.5 s target is not reachable on this stack**: Flux ~0.3 + Haiku ~1.25 + Aura ~0.3.
- **Cut:** the first clause of a reply goes to the voice the moment its mark and a space arrive (`pipeline.clause_aggregator`); words written before a tool call are said when the call starts (`_words_done_frame`; before, they waited until the call was written out); the desktop block is read while the user talks and a recent read serves the reply (`Hands.prefetch_desk`, `for_call` "ahead"; the first turn waited its whole 250 ms for a cold read). End of speech -> first audio p50 2,528 -> 2,297 ms (hand-offs 2,957 -> 2,422, hands 2,485 -> 2,256, chat 2,337 -> 2,241).
- **Thinker:** one call is Sonnet's first token 1.9-2.1 s (22k-token cached prefix, ap-south-1; us-east-1 2.8 s; effort low or none the same) plus the tool call's ~150-170 output tokens (~1.1 s): 3.1-3.3 s. What cut was fewer calls (act first, v3.6) and the warm cache; `Agent.warm_cache()` / `idle_s` are public now.
- **One-breath wakes:** 72 "Yuki, <request>" clips (six voices) and 90 others (36 sound-alikes: "yucky", "you key in", "you keep"): the spotter missed 14/72 clean (36/72 at 10 dB speech noise), half of them because a sound-alike variant won. No threshold, boost, path count or variant set fixed it without false wakes (e.g. 8 paths: 9 misses but 3 false; YUKI boost 3: 11 and 4). Kept: on a near miss the phoneme model re-reads the last 3 s (`wake.NameCheck`, threshold 0.4, loaded on the first near miss, 1.4 s and +57 MB, let go after 10 min unused). Through the real listener: woke 59 -> 62 of 72, false wakes 0 -> 0 of 90. A rescued wake is not treated as certainly addressed (the mouth judges). Needs the zh-en model (present on this PC; a fresh install has no second opinion until it is downloaded).
- **Bugs:** `media_key` takes `want` (playing / paused): already in that state, nothing is pressed and the report says so ("It's already paused."), and verified means it reached that state. The thinker's done "never what you are about to do". Root cause of "Making that receipts folder now": the front desk (the worker busy) was shown only the look tools, so it could never reach for hands and the request was never queued; it now sees every tool, actions answered by its blocked backend, which queues the request for the worker. Doubt notes: a low-confidence word counts only with 5+ letters (below 0.4 any word): on 100 clear utterances flagged turns 12 -> 7, 6 of the 7 real mistranscriptions.

## 1. The idea in one picture

Two models, running at the same time, with one job each (gradient-bang's shape: one talker inline, one thinker in the background):

- The **mouth** (the talker, Claude Haiku 4.5) owns the conversation. It decides every turn: it answers alone only social turns and what is literally in front of it (the time, what it said, the user's rules, a result it has, one plain fact from the grounding lookup), and hands everything else to the thinker.
- The **brain** (the thinker, the existing `Agent`) owns everything that needs judgement, memory, reasoning or hands. Its outcome, questions and failures go through the mouth, and when is decided by the narrator gate. **One voice (v3.14):** the few words it writes for a step (`say_now`) and its `say` lines are said by code in Yuki's same voice when a pause would be noticeable (§6.3), and go into the mouth's context as Yuki's own words, so the mouth knows everything that was said. Never two personas, never its reasoning, never a line twice.

|---|---|---|
| mouth → brain | a new task; a correction/addition to a running task; an answer to the brain's question | `tell_yuki(request, context?, intent)` → `VoiceBridge` → `AgentRuntime.submit` / `.steer` / `.answer`; a correction to a task that is finishing starts a new task quietly |
| mouth → brain | stop | Pipecat's built-in `cancel_tell_yuki` → `AgentRuntime.cancel(job_id)` |
| brain → voice | a step it is taking (v3.14) | the step's `say_now` (streamed as `Partial("step")`, `runtime.partial`) → `StepLines` → a `TTSSpeakFrame` into a noticeable silence; the words land in the mouth's context and the job's log (§6.3) |
| brain → voice | progress worth saying | brain tool `say(text)` → `said` signal → `StepLines` (waits only for the user and Yuki's own speech; v3.14, was a mouth run) |

Pipecat's **async function calls** (`register_function(..., cancel_on_interruption=False, cancellable_by_llm=True)`) carry them: the mouth keeps talking while the tool runs, intermediate results stream back, and the mouth can cancel the call.

## 2. Rules for the voice layer

1. **One voice (v3.14; was "only the mouth speaks").** Everything is said in Yuki's one voice and lands in the mouth's context as her own words. The brain's outcome, questions and failures reach the user only through the mouth; its step lines (`say_now`) and `say` lines are said by code, unchanged, into a noticeable silence (§6.3), never over the user, never twice, never after its outcome is known. Yuki never speaks first: nothing is said for a job the user did not ask for (proactivity is cards only).
2. **Every spoken claim traces to a result or an event.** Results arrive only through the tool channel; progress lines come only from the brain's real tool calls; "how's it going?" is answered only from the task's action log; grounded facts come only from memory's own lookup. The final payload is `result`, not `done` (a `done` key made the mouth say "all set" over a result that said nothing was done), and it says what to do when it does not answer the question (measured: given "Done." for "what did Rohan say?", the mouth invented "Rohan said it's sorted").
3. **No keyword routing.** The mouth decides by which tool it calls and with what `intent`; the bridge routes on job state only; the gate on conversation state only.
4. **Say it when a person would.** The narrator gate (§6.4) holds everything while the user talks or Yuki owes a reply, lets it settle, waits out a cooldown, and folds stale results in silently.
5. **Tools never run on a guess.** A speculative reply (eager end of turn) holds its words and its tool calls until the turn is confirmed, and drops both when it is withdrawn (§9).
6. **Barge-in stops the voice, not the work.** Ending a conversation never cancels a brain job either; only `cancel_tell_yuki` and the cancel hotkey do.
7. **Log everything, words nowhere but memory.** The voice log is content-free (timings, sizes, tokens, cost, language, states, errors, gate decisions). What was said goes only to the encrypted conversation memory through `log_turn`. The action logs used for progress answers live in memory (RAM) only. Pipecat's own logging is warnings-and-errors into a file.
8. **Keys from the environment only:** `DEEPGRAM_API_KEY`, `GOOGLE_API_KEY`, `ELEVENLABS_API_KEY` (read from `os.environ`, else `HKCU\Environment`), `AWS_BEARER_TOKEN_BEDROCK`. Nothing prints or stores a key.
9. **Voice off costs nothing; the wake word alone costs little.** Off: no thread, socket, model or open device, and importing the voice package imports no Pipecat, sounddevice or sherpa-onnx (tested). Wake-only: the spotter and the mic, nothing of Pipecat, Deepgram, Anthropic or onnxruntime (measured, §23).

## 4. Process and thread model

Voice runs inside `yuki-ui`. Threads, only while their state is on:

| Thread | When | Owns | Crossings |
|---|---|---|---|
| GUI (Qt) | always | tray, pill, hotkeys, `AgentRuntime`, `VoiceBridge`, `VoiceSession` | Qt signals |
| PortAudio callback | mic open (wake on, or a conversation) | `SharedMic`: 20 ms blocks, fan-out, 3 s in-memory backlog | subscriber callbacks only hand blocks over |
| `yuki-voice-wake` | "Listen for 'Yuki'" on (calls too, v3.4) | `WakeListener`: 100 ms batches, sound gate, spotter (restarted on each sound episode) | Qt signal on a hit |
| `yuki-voice` | a conversation | `asyncio.run(Conversation.run())`: the Pipecat pipeline | bridge: Qt signal carrying a callable into the GUI thread; `call_soon_threadsafe` back |
| `yuki-voice-out` | a conversation | blocking speaker writes | executor |
| `yuki-voice-ground` | a conversation, grounding on | the memory lookups (§5.5) | futures polled by the mouth's call, bounded |

- Nothing on the voice loop calls a blocking Yuki function. Memory is read before the loop starts (bounded 3 s); `log_turn` is Yuki's own queued writer.
- Every crossing is one-way and explicit (`yuki/voice/bridge.py` module docstring).
- **Start** is a no-op when a conversation is on. **Stop** asks the pipeline to end and the thread joins (bounded 5 s at quit); the speaker closes; the mic closes unless the wake word still needs it.

## 5. The mouth (`yuki/voice/mouth.py`)

### 5.1 Prompt (behavioural, v3)

Sections, in prose with worked examples: **Two halves** (you are the talker; the thinker has eyes, hands, memory and judgement; one Yuki to the user). **What you answer yourself** (only social turns, including reacting to what they tell you about their day or plans, and what is literally in front of you: the time, what you said, their rules, a result you have, one lookup fact that plainly answers a simple stable question) **and what you hand over** (everything about their activity, day, memory beyond that one fact, files, people, plans asked about, decisions, anything to do or look up; when unsure, hand over). **The lookup block** (nearest items, mostly unrelated, never the whole record; never add up, never fill a gap, never say something did not happen). **Commitment discipline** (gradient-bang's rule: "let me check" means the tool call is in the same reply) with worked bad/good pairs: the promise without a call, the guessed day, the memory question with and without a matching lookup fact, the "no, you didn't" from an incomplete lookup, the invented answer to a "Done." result, repeating a result when they want more. **The hand-over** (`request` = their words and scope, `context` = only references; nothing added from what you know or the lookup; bad/good pairs). **While the thinker works** (progress, yuki_says, yuki_asks, status, result, failed, held_back; condensed results and "want the rest?"; never talk about results or tools as such; `check_progress` only for a task already handed over). **How you speak** and **their rules** (unchanged from v2).

The core is frozen per conversation; Pipecat's async-tool paragraphs follow it (its em dash is replaced by a comma). Pipecat's final-result note ("must be conveyed even if the conversation moved on") is replaced at build time by one that defers to the payload, because the gate now decides that (`pipeline.FINAL_DESCRIPTION`).

**Measured with real Haiku (text-level probe, 6 samples each, 2026-09-25):** memory question with no lookup fact → hand-over 6/6; a greeting after the name → answered alone 6/6; the user telling their weekend plan → answered alone 5/6 (1/6 handed it over); "tell me the rest" after a result → `more_of_result` 6/6. In the audio scenarios (§23) the remaining misses were: repeating a result for "tell me the rest" (1 of 2 runs), and handing over the weekend plan (2 of 3 runs, before the "telling you is not asking" wording).

### 5.2 Tools

- `tell_yuki(request, context?, intent: new_task|follow_up)`: async (`cancel_on_interruption=False`, `cancellable_by_llm=True`, no timeout). `request` is the user's ask; `context` only resolves references; the brain is told which is which, with the user's last three utterances as heard (`brain_request`).
- `cancel_tell_yuki` (Pipecat's): a successful cancel settles without another mouth turn (the mouth says "stopping it" in the same reply; the extra turn made it greet the user out of nowhere, measured). A refusal still gets a turn.
- `check_progress(question)`: sync. If the task has finished and its result is still waiting in the gate, that result goes into the context there and then and is the answer (no model call). Otherwise one isolated Haiku call (`progress.TASK_PROGRESS_PROMPT`, adapted from gradient-bang's `task_progress.md`: "Do not make up information that is not in the log") over that task's action log and the user's question, nothing else; ~1 s, ~$0.0005.
- `more_of_result()`: sync, instant: the next 1–2 sentences of the last result that had more. With nothing left it says so and that more detail is a new `tell_yuki`.
- **v3.2:** `check_progress` in a run the user did not start (a progress line, a result, a hand's report) is settled quietly with "nobody asked" (`bridge.user_turn`, a state fact; live: it called it twice on its own). `stay_quiet()`: the mouth's way to say nothing on such a run (settled without a turn). The six hands (§5.6).

### 5.6 Hands (`yuki/voice/hands.py`, v3.2, v3.3)

gradient-bang's voice LLM calls its quick tools itself; so does the mouth. Tools (v3.5): `media_key(key, times?)` (media keys and the SYSTEM volume), `app_volume(app, change|level|mute)` (one app's own mixer volume), `scroll(window, direction, amount?)`, `window(window, action)`, `tab(window, action=show|close|reopen, tab|tabs, named, expect)`, `open_url(say_first, url, app?)`, `open_app(say_first, name)`, each with a required `say_when_done`. `press_keys` was removed in v3.5 (the talker has no keyboard; keys are the thinker's, which looks first). They run the brain's backend functions (`yuki.actions`) off the loop, with the brain's guards: keys and scrolling go to the named window only while it is in front (`expect_hwnd`; it is brought forward first); a hwnd, or a tab, not in this call's desktop summary is refused. Without a worker backend (a stand-in brain) there are no hands, never the real desktop.

- **Instant hands (v3.3):** `press_keys`, `media_key`, `scroll`, `window`, `tab` are called alone, with no words before them: Pipecat runs a tool call when the reply's stream ends, and a reply that is only the call ends the moment the call is written. The words-first reply of v3.2 made the user hear the whole sentence before anything moved (live 18:55: "okay I'm scrolling this window…", then the scroll). `open_url` and `open_app` take seconds, so they keep a few words first, like `tell_yuki`.
- **Done line (v3.3):** said at once by code (a `TTSSpeakFrame`, no second model call) only when the hand's report says `verified` True: `window` from `window_action`'s observed state; `tab` from the tab's `IsSelected`; `scroll` from the scroll position (below); a transport key from the media session's status or track; a volume key from the output volume (`perception.audio.master_volume`, read-only); `open_url` from the page at the address **and** titled (the hand then waits up to 6 s for the title, reading the tab strip; live "YouTube's up" came while the page was still blank); `open_app` from `launch_app`'s window in front. Otherwise the report goes to the mouth as `not_verified` / `failed`, and the mouth says what it shows and hands it to the thinker (not when the report says why nothing more can happen, e.g. already at the bottom). `press_keys` always reports back (a key has no verdict).
- **Scroll (v3.3, `yuki/actions/scrolling.py`, also the brain's `scroll`):** the hand aims at the window's centre, never the cursor. The scroll finds the scrollable element at the point or its nearest ancestor with a UIA `ScrollPattern` on that axis, else the window's largest one; moves it with `SetScrollPercent` (a screenful per 10 notches, from its view size; the pattern's own increments when a provider has no `SetScrollPercent`); and polls the percent (≤ 0.8 s). With no pattern anywhere: the wheel at the point, then the cursor back where the user had it (≤ 0.15 s), verified by the element under the point moving. The result says which, with the numbers ("scrolled Document "YouTube" down: 12% -> 31% of the way (UI Automation; the cursor was not moved)"); `ok` False when it provably did not move or is at the end.
- **Tabs (v3.3):** the desktop block's `tabs of [hwnd] (n, * = the one showing): 1 "…"; 2* "…"` line is the foreground window's own strip (`perception/tabs.py`): TabItems outside any Document, grouped by parent, the biggest group in tree order; page content is never walked; ≤ 700 nodes, 0.15 s. Read ahead on a thread when the user starts talking, reused while the window title and the action log are unchanged (≤ 20 s), else read on the summary's path. The `tab` hand re-reads the strip and refuses if the name at that place changed.
- **Action log (v3.3):** each hand (and each thinker action tool, `ACTION_TOOL_NAMES`) adds a line: time, who, what, verified / not verified / failed, the report (verified facts first). The mouth's block carries the last 4 (240 chars each), `brain_request` the last 6 ("[Done on the desktop earlier in this conversation …]"). RAM only (titles and addresses are content).
- **Desktop summary:** the brain's `format_overview`, one media line, the tabs line and the action log, captured for every mouth call in parallel with the grounding wait (bound `voice_desk_wait_ms` 250), in the volatile block. *Measured:* 346-370 chars on the stub (665 on this PC) before v3.3; logged as `desk`, `desk_ms`, `desk_chars`, `desk_tabs_ms`; `eos_to_action_ms` is new in the turn log.
- **Choice:** the prompt's "# Your hands" section with worked good/bad pairs (one step on something the block shows → a hand, called alone; a tab is not a window; open_url opens its own tab; a repeat is the same hand; two steps, anything inside a window, memory, uncertainty → `tell_yuki`). No word lists.
- **Click and type (v3.14):** hands for what the user points at on the screen, both instant and verified by code. The desktop block has an **items line**: the window in front's links, buttons and list rows (UIA, `screennames.ITEM_ROLES`), page content first (by the Document parent chain), deduplicated by role and name, at most 20, names cut at 60 characters, numbered for the hand, read while the user talks (`Hands._read_items`, fresh 4 s, read ahead 3 s; one tree read serves the names line too). `click(window, item, named)` clicks by the read it came from (the dispatcher's `click(element, read, expect_hwnd)`), found again by role and name when that read is old, refused (and passed to the thinker by code) when it cannot be found or the number was never on the line; verified by `loop.action_verdict` from the input layer's watch (the page, the focus or the window changed). `type(window, text)` types only into the field the **focus line** names (`focus_snapshot`: accepts text, not a password, the same window), verified by reading the field back. Keys and shortcuts stay the thinker's. A repeated identical done line within 60 s is not said again. Offline (hands314): "play the second one" clicked and playing 2.4-2.6 s after the end of speech, "type hi" typed and read back 1.9-2.9 s after, no thinker call.

### 5.3 Context

Once per conversation, off the loop: `MemoryAccess.context(query="")`. No query: this read is for the mouth's cached layers only (its profile and rules), before any words. (The v3 reason, "a query loads the ~600 MB embedder", is gone since v3.1: the embedder is the memory service's, int8 MiniLM ~176 MB in that process, served over its pipe, nothing loaded here.) What memory holds near the user's words comes on every turn from the grounding lookup (§5.5): `voice_grounding_source` `related` (v3.14 default: the memory builder's `MemoryClient.related_text(voice=True)`, ranked across all of memory against the words, the screen and the current thread of work, each line with where and when it came from; its index is built when the conversation starts, `warm_related`) or `relevant` (fast memory and know-how by the words, v3.5-v3.13, and the fallback where memory has no `related_text`). Measured: with a 1.36k-character related block the talker's first token p50 1,770 ms vs 1,723 ms with a 1.05k-character fast-memory block and 1,745 ms with none (12 interleaved rounds, `voice_ttft.py`); in replays the related lookups took p50 49 ms (max 446) vs 80 ms (max 879), and no loop stall ≥ 300 ms came with them. The mouth's prompt uses only the Personality section (≤ 1,500 chars), the user's names and the rules and preferences of the standing context, as their own layers; the rest of the portrait, the to-dos and the resume are not given to the mouth (they were the source of v2's memory-answer failures).

### 5.4 Caching, keep-alive and warm-up (measured)

- **Layers:** core (+ tools, which carry none), profile, rules: cache breakpoints on profile and rules, Pipecat's on the last two user messages. The v3 core with a real profile is ~4.7k tokens, above Haiku 4.5's 4,096-token minimum, so it caches without padding.
- **The volatile block** (the time now and the grounding lookup) is appended to the newest user message, after every breakpoint (`pipeline.with_volatile`). In v3's first draft it was the last system block, which sits before the conversation: every turn then re-wrote 1–2k tokens of history (measured cache writes 826–1,930 per turn); now a turn writes ~20–400.
- **Caching and speed:** cached 960 ms vs uncached 1,012 ms time to first token (p50 of 5, 4.7k-token prompt): it saves ~90% of input cost, not time.
- **Keep-alive (the "unexplained ~0.7 s"):** httpx drops an idle connection after 5 s, so every turn after a pause paid a new TCP+TLS handshake to Bedrock. Measured from this PC after 8–20 s idle: first token p50 1,362 ms with the default client vs 860 ms with the connection kept (`pipeline.bedrock_client`, `keepalive_expiry=300`). Pipecat's own overhead is negligible: building the request ~1 ms, context hand-over ~16 ms, TTFB metric = time to the first content block.
- **Warm-up:** each conversation has its own client, and a one-token request opens its connection while Deepgram connects.

### 5.5 The grounding lookup (`yuki/voice/grounding.py`)

On every user turn the mouth sees what memory holds near the user's words, so it can answer a plain stored fact ("who's my accountant?") at once, or know to hand over.

- **What runs:** `MemoryClient.recall(words, limit=12)` (local embedder + keyword search, no model call) on one worker thread, keeping journal facts, episodes and weekly reviews (not past chats or session summaries, which are Yuki's own earlier words), top 4, dated, a joke or uncertain item labelled.
- **Speculative:** each Flux interim update starts a lookup (one in flight, newest words win); the final transcript starts one more if the words changed. The mouth's call waits at most `voice_grounding_wait_ms` (60 ms) for the final one, else takes this turn's freshest finished lookup, else goes without (a previous turn's lookup is never shown for a new user turn).
- **Measured** (real database copy, 684 facts, 52 episodes): recall 30–50 ms standalone; in a running conversation p50 52–56 ms, max ~330–500 ms; added wait on the mouth's call p50 0.5 ms, max 66 ms (the lookup is usually done before the transcript is final). About 30–95 lookups per 2–3 minute conversation.
- **RAM:** the embedder is memory's process-wide one (~550 MB loaded; the brain loads the same one for know-how on its first request anyway). It is loaded in the background when a conversation starts (2–3 s) and unloaded when the conversation ends if the conversation loaded it and no brain request is running. `voice_grounding = False` turns the lookup off and keeps a conversation at ~240 MB.

## 6. The bridge, the action log and the narrator (`bridge.py`, `progress.py`, `narrator.py`)

### 6.1 Jobs and routing

- **Job ids** are the runtime's request ids. `tell_yuki` `new_task` → submit the request (+ context and the last three utterances). `follow_up` → the newest unfinished voice job, decided on the GUI thread at that moment (a future the handler awaits): waiting for an answer → `answer`; running → `steer`; queued → held and delivered when it starts; **finishing or finished → a new task, quietly** (gradient-bang's `task_closing` path): the addition goes to the brain with the earlier request and its outcome as context, and this call carries the new task's outcome. A follow-up that was routed settles at once without another mouth turn.
- **Front desk / handed off / late corrections** as in v2 (`handed_off` re-keys the job; `steer_unread` runs a too-late addition as its own request, its result through the gate).
- **A question nobody answered never holds the worker (v3.14):** a job that asked the user holds its lane until they answer (the lane waits with no end). When new work goes to the worker (a hand of the talker's that did not take effect, or `tell_yuki` new_task with `acts`) while a voice job on it waits for an answer, the talker has already judged the new words a new request, not the answer: that question is passed over and its job withdrawn, unsaid (`VoiceBridge._pass_over_questions`, logged `question_passed_over`). Offline before this, zen928's unanswered "which video?" held "Pause it." and "Open WhatsApp." until the run timed out.
- **A "still on it" reply is never stale (v3.14):** the talker's reply to a waiting line is dropped unheard when that job's outcome became known before its first audio (`VoiceBridge.waiting_reply_stale`, asked once by the voice right before the reply would be heard; the gate holds the outcome until then). Offline warp929: "Still looking for it." had been said after the tab had switched.
- **Nothing done is never said as done (v3.14b):** a `done` result whose request asked for something to happen (tell_yuki `acts`, or a hand of the talker's was tried first) while no action of its job succeeded carries `nothing_done` and `NOTHING_DONE_NOTE`: the talker says what was found and why nothing was needed, or that it did not do it, or asks (offline a misheard "Ok on WhatsApp" was answered "Got it." with nothing done). From the job's record (the runtime's tool signals), never from the words.
- **A result said in the same reply as stay_quiet is said once (v3.14):** the "a result is always said" refusal of stay_quiet applies only when the reply said nothing aloud (offline hands314: the same outcome twice).
- **A conversation ending** detaches every handler queue: the job keeps running and its result lands as a card/strip.

### 6.2 The action log (`progress.JobLog`)

Per job, in RAM only: the request, each tool call (label and a few short inputs: query, since, until, group_by, app, url), each result's one-line summary, `say` lines, questions, the user's additions, the outcome. It feeds `check_progress` and nothing else.

### 6.3 Step lines in one voice (v3.14; was progress from real events)

The thinker writes a few words for each action or slower read of a voice request (`say_now`, the first field of the call, `tools.STEP_TOOLS`: "Switching tabs.", "Trying F11 for full screen."). They stream out the moment that string is complete (`stream_partial.string_value`, `Partial("step")`, `runtime.partial`), or come with the finished call. `yuki/voice/steplines.StepLines` decides by code when each is said, straight into the voice (a `TTSSpeakFrame`: no mouth run, which cost ~2.5 s and made v3.9's per-step lines stale), and never reads what they say:

- While its step runs: after `voice_step_silence_s` (2.5 s) of nobody speaking and `voice_step_after_s` (0.8 s) into the step, or at its start when the silence is already `voice_step_long_silence_s` (5 s).
- Never once its step has returned (v3.14b; v3.14 also said a quick step's line in a long silence after it, which is a stale line: "Switching tabs." after the switch). A quick step (most clicks and keys end in under 0.4 s, measured) is rarely narrated; the pauses between steps are the one "still on it" line's.
- Never over the user (their speech, or the mic hearing them first), never while Yuki is mid-sentence or words are on their way, never in call mode, never once the job's outcome or question is known, never the same words twice in a conversation, at most 12 s after it was offered.
- The thinker's `say` lines wait only for the user and Yuki's own speech.
- v3.14b: `say_now` is required on a spoken request's step tools (`tools.with_step_lines`; the fast first pass left it out of 12 of 13 steps of a long search), and a step line whose step returned before its first audio is dropped unheard (`StepLines.line_stale`, asked by the voice right before a reply's first audio: the voice's first byte is ~1 s after the line is sent).

Every line said goes into the mouth's context as Yuki's words (Pipecat appends what a `TTSSpeakFrame` played) and into the job's log (`VoiceBridge.step_said`, for "how's it going?"); the spoken-line check still hears it first. Logged `step_line` (offered / spoken / dropped with why, waits, silence; sizes only). The dead v3.9 relay (`progress_payload`, `StepPacer`, the mouth's "step" item) is removed. The "still on it" line (`_wait_check`) stays for silences no step line fills: one for an acknowledged job, up to `voice_progress_lines` otherwise (v3.10-v3.13 capped it with `min(1, …)`), each after `voice_wait_line_s` of silence, naming the thinker's own step line.

### 6.4 The narrator gate (`narrator.NarratorGate`)

Every brain→mouth item (progress, say, ask, result) waits here, then goes into the context. **Only the talker speaks (v3.10):** nothing of the thinker's is ever said by code; each item is an event the talker says, once, in its own voice (a verified finish is released after only the short final gap and marked `verified`).

| Gate | Rule |
|---|---|
| user talking | Flux says the user is speaking, **or the microphone hears speech Flux has not reported yet** (its start of turn comes ~0.5–1 s late; measured: a result started over the user before this). A stretch of sound over 6 s without a turn counts as noise. |
| Yuki busy | speaking, generating, or one of its quick tools in flight |
| owes a reply | the user's last turn has not been answered yet (8 s at most) |
| cooldown | `voice_cooldown_s` (1.5 s) after Yuki's own speech; progress lines only after `voice_progress_pause_s` (8 s, v3.2) of Yuki's silence, so a quick job is never narrated and a result that lands first replaces them |
| settle | `voice_settle_s` (1.5 s) since the last item, at most `voice_settle_max_s` (6 s) from the first: near-simultaneous items become one turn (delivered together, one mouth run, results last) |
| stale | a progress line or `queued` that waited through one user turn is dropped; a `say` through two; a result through `voice_stale_turns` (3) is folded in silently as `held_back` (the mouth answers from it if asked). A question is never stale. |

**v3.14:** a result or a question waits only for the user and for Yuki's own speech (the first rows): no gap, settle or cooldown (live 27-29 Sept results waited p50 0.9 s, max 11.1 s, 2.2 s of it in all on the gap). Step lines do not pass through the gate (§6.3).

A newer item of a job replaces its waiting lower-ranked ones (a result makes a waiting progress line pointless). Cancelling a task drops its waiting items. The gate's waits and decisions are logged (`narrator` events, content-free); a quiet conversation stays open while the gate holds something.

### 6.5 Condensation (`narrator.condense`)

Before the mouth sees a result, code keeps the first `voice_result_sentences` (2) whole sentences within `voice_result_chars` (280; a single longer sentence is cut at a clause boundary with "…"); list items count as sentences. The rest is kept on the job for `more_of_result`, and the payload says `more_available`.

## 7. Brain changes (small, text mode benefits too)

- **`Agent.steer(text)`** (`loop.py`): a thread-safe inbox drained at each step boundary into the next tool-results message as `[The user added while you were working]: …`. A `done` (or a plain-text final) with a non-empty inbox is held: the model is told its message was not sent and takes one more step. Logged `steer`. `take_steers()` returns what came too late.
- **`say(text)`** (`tools.py`, a control tool, runs mid-stream, returns "Said. Keep going."; `loop.py` yields `Say`, logs `say`); `runtime.py` emits `said`; text mode shows it in the strip.
- **Voice profile (v3.2, `ui/runtime.py`, `Agent.run(model=, thinking=, lean=)`):** chosen by the job's source: `voice_brain_thinking` False (thinking disabled), `voice_brain_portrait` False (the rest of the portrait and the resume left out; profile and rules layers, to-dos, know-how, commitments stay), `voice_brain_model` (empty = the brain's). *Measured* first model call, 6 tasks on the stub desk (minimize, scroll, pause, open YouTube, two-step Spotify, yesterday afternoon): before 5.2/5.2/3.1/4.5/5.2/4.2 s ($0.23); Sonnet lean 4.4/3.4/2.9/3.2/2.4/2.8 s ($0.13), same tool choices; Haiku 4.5 lean 2.6/1.7/1.6/1.4/1.5/1.6 s ($0.05) but it answered "YouTube's open" after only focusing Chrome and "focus playlist playing" unverified, so Sonnet stays. Haiku needs `voice_brain_effort = ""` (it takes no effort parameter).
- **Fast first, escalate on evidence (v3.14, `Agent.run(escalate=)`):** a spoken request starts at `voice_brain_effort` low with thinking off and moves, once, to `voice_brain_escalate_effort` medium with adaptive thinking for the rest of that request on a measured signal only: an action failed or its own report does not verify its effect, the loop breaker tripped, the user was asked, a finish or a claim had no evidence, or a tool call came back written as text (`_step_signal`). Escalating on an unverified or failed action adds a rethink note. On Sonnet 5 effort is part of the cached prefix from the tools on (an effort change is a full cache miss, ~$0.06 per escalation); a thinking toggle invalidates only the messages. `warm_cache` warms the voice profile's entry.
- **A state claim needs evidence (v3.14):** `finishes_with` ends the request only when the action's own report verifies its effect (`loop.action_verdict`: `details.verified`, `page_verified`, a read-back, or the input layer's `foreground_changed` / `focus_changed` / `foreground_title_changed` / `page_changed`); each action result carries "(Verified from its own report: …)" or "(Not verified: …)". `done(message, about)` names the windows whose state the message asserts; with no look or verified action on them in this request it goes back once (`CLAIM_ROUNDS`, the note labelled as Yuki's check, not the user).
- **v3.14b:** a question never holds its lane (parked after `ask_park_s` or when a newer request waits, carried on by a later answer; ARCHITECTURE.md); keys report the window's state before -> after and `window_action` is the one-step way to change it (the brain prompt and the hotkey tool say so); a result with no successful action for a request that asked for one is `nothing_done` for the talker (§6.1).
- **Steer and cancel reach a running read (v3.14):** read-only tools and the view after an action run through `Agent._race` (polled every 50 ms): a cancel or a steer leaves a slow read at once (its result is dropped, the breaker ignores it); actions always finish.
- **Cancel checkpoint** after each model call: a text-only reply that finishes after a cancel is not delivered as the final word.
- **Prompt** (`prompt.py`, one separate paragraph): voice requests are listened to, so use `say` at the moments a helper would speak up, above all when part of the answer is found while more remains; and a microphone held by Yuki's own program is its voice listening, not a call (§7.6 of v1). *Measured:* in three live runs (tasks of 55–165 s) Sonnet at medium effort **did not call `say`**; the mouth covered the silence by answering "how's it going?" from the job table. Since v3 the silence is covered by progress from the brain's real tool calls (§6.3) and `check_progress`; `say` stays for what the brain itself wants heard.

## 9. Turn-taking and interruptions

- **Flux owns turns** with its recommended strategies passed explicitly to the user aggregator (`stt.recommended_user_turn_strategies`); left to default, the aggregator first built Pipecat's local ones, which imported onnxruntime and loaded the Smart Turn model in every conversation (measured). `eot_threshold` 0.7, `eot_timeout_ms` 5000.
- **Eager end-of-turn: evaluated, kept off.** Clips with natural 0.9 s pauses mid-sentence (`scripts/voice_clips.py --set v3`, 7 clips, 5 with pauses): no setting made Yuki speak over the user (Pipecat holds a speculative reply until the turn is confirmed, and a reply takes > 0.9 s, so resuming always won). Flux ended the turn inside a pause (a wasted mouth call, then one reply to the whole sentence) 3/7 at eot 0.7 without eager, 2/7 with eager 0.5 or 0.4, 5/7 at eot 0.6. End of speech → first audio p50 on those hand-off turns: 2,870 ms off, 2,884 ms eager 0.5, 2,458 ms eager 0.4. **But in the full scenarios eager 0.4 double-fired**: two replies to one "thanks", and a duplicated `tell_yuki` (a second brain job for the same question) in 2 of 3 runs; and the full-scenario p50 was no better (2,320 ms eager vs 2,256 ms off). Off until Pipecat's speculation handles tool calls without duplicates; `voice_eager_eot_threshold` stays a setting. eot 0.6 cut sentences too often.
- **v3.5: eager end-of-turn on (0.4).** The duplicates were a race: Flux's proposed turn stop and the stop strategy's transcript timer resolve the same turn within a millisecond, and Pipecat's `EagerUserTurnStopStrategy` awaits inside its resolution, so the second call ran a second inference whose turn-stop released the speculative reply, then the first ran a third (Pipecat debug log, 2 replies to "Hello?", two answers to "what's the CLI setup?"). `pipeline.one_stop_per_turn` serializes the resolutions, one per turn. Pipecat withdraws a speculative reply that calls a tool (then asks again); here its calls are held and run the moment the turn is confirmed (`run_function_calls` / `push_frame` in the service subclass), dropped with its words on a withdrawal. After the fix: 0 duplicate replies in 14 eager turns (§27).
- **Audio before STT is connected is held** and released in order; the quiet-time clock starts only once it is connected (a slow Deepgram connect once ended a test conversation before it heard anything).
- **Mic frames of 80 ms.** **Barge-in**: Flux StartOfTurn → InterruptionFrame; ElevenLabs word timestamps keep only the heard words in context.
- **Keyterms** (v3.5, `yuki/voice/keyterms.py`): "Yuki", `Settings.user_names`, and the subjects of memory's person facts plus short proper names of work and interests (read once per conversation through `MemoryAccess.call`, at most `voice_keyterms_max`); open loops are left out (one held "Barun", the misheard Varun). Measured (§27): on `flux-general-multi` keyterms barely bite (11 → 13 of 30 name clips); on `flux-general-en` 13 → 23 of 30. The app keeps `multi` for Hindi; switching `voice_stt_model` is the user's call.

## 10. Voice

**Since v3.8 (2026-09-27): Gemini TTS, voice Leda** (`yuki/voice/gemini_tts.py`, `yuki/voice/expressive.py`; the user's choice: "just use the google api key, and set the voice").

- **Model** `gemini-3.8-flash-lite-tts` (Flash Lite: first audio ~1.0-1.3 s; `gemini-3.8-flash-tts` ~1.8 s), prebuilt voice **Leda**, key `GOOGLE_API_KEY` (user environment variable, read from `os.environ`, else `HKCU\Environment`, like every key). AI Studio REST: `models/{model}:streamGenerateContent?alt=sse`, header `x-goog-api-key`; the SSE events carry base64 `inlineData` of `audio/l16; rate=24000` mono PCM, played as it comes.
- **Why not Pipecat's `GeminiTTSService`:** it needs google-genai and google-cloud-texttospeech (neither installed, both heavy). Ours is ~400 lines on `aiohttp`: one session per conversation (up to 4 connections kept open, pre-opened at the start and again before a reply when unused for 45 s: TLS was measured to be only ~0.1 s of the wait).
- **Pieces in parallel, played in order:** each piece the aggregator hands over (the first clause early, then sentences) is requested at once, alongside the ones before it; a player per reply plays them strictly in order and releases each piece's words (`TTSTextFrame`) after its audio, so the context keeps only what was heard. Interruptions cancel every request and player of the conversation.
- **Expression, chosen by the mouth** (its "# Your voice" section: when a person would, never by code; plus "write for the ear": openers, contractions, short sentences, the odd self-correction): Gemini's sound tags where the sound belongs, written by the mouth in square brackets (`[laugh]`, `[sigh]`, `[gasp]`, `[phew]`, `[short pause]` ...) and sent in Gemini's own spelling (`<laugh>`); a mark Gemini does not document is cut out, never read as words. And an optional style mark first in a reply, `[style: calm and soft]`, reusing a small set of short styles ("warm and teasing", "calm and soft", "quick and upbeat", "gentle and sympathetic", "whispering", "surprised", "sleepy and soft", "excited"). The style goes out as the request part's `speechMetadata.style` on **every piece of that reply**, so the mood never changes mid-reply. (Found by probing 2026-09-27: the docs show style only for the Interactions API, `speech_metadata`, which starts ~0.5 s later and streams at real-time pace; `generateContent` accepts `parts[].speechMetadata.style`, rejects unknown fields, and honours it: whispered RMS ~0.5x, shouted ~1.8x of plain.)
- **Why square brackets:** the first build told the mouth to write Gemini's angle-bracket tags. In two offline runs Haiku then wrote XML-like markup as speech in 5 result turns (`<thinking>` with its reasoning inside, `<stay_quiet></invoke>` instead of the tool call, a lone `<style: ...>`). With square brackets and "nothing else in brackets, never your thinking or a tool's name as words" it did not (runs below). Angle-bracket marks and closing tags are still recognised, so stray markup is cut out and never said or shown.
- **Clean words everywhere else:** `expressive.strip_tags` (a structural cut of our own fixed `[...]` / `<...>` syntax) runs on the chat's `assistant_speech`, the hand-step args, and the reply memory logs; Aura and ElevenLabs are sent the words without marks (`_clause_tts(strip_marks=True)`). The mouth's own context keeps its marks, so it sees how often it used them.
- **Seams:** Gemini pads each request with 60-250 ms before and up to 430 ms after the words; `EdgeTrimmer` keeps 30 ms and 150 ms (level 250 per 10 ms window, 4 ms fades), so sentence gaps measure 110-210 ms and the first word comes sooner.
- **Fallback:** a piece with an HTTP error, a quota refusal or no audio within `voice_gemini_first_audio_s` (3 s) is said by Deepgram Aura (REST, same 24 kHz PCM, marks stripped), and so is the rest of that conversation; a quota or key refusal also makes the next conversations start on Aura for 10 min (`gemini_tts.gemini_status`, used by `preflight`, which also does one free model GET per 10 min, cached, refreshed in the background). No key: Aura, with a note in the pill.
- **Voice cache (v3.14, `yuki/voice/ttscache.py`):** a line of at most 6 words and 60 characters that the voice fetched whole, never cut, is kept on disk (24 kHz PCM, edges already trimmed) keyed by its exact words (marks included), the voice, its model and the reply's style; said again, it plays from disk with no request (first audio ~0 ms instead of ~1.0-1.3 s). The spoken-line check's own SAY for such a line as a reply's first piece is remembered with it (only for lines it lets through unchecked anywhere else, at most `FREE_WORDS`): said again as a first piece it needs no model check (~0.9 s). A DROP is never remembered. At most 300 lines, least recently used let go, in `%LOCALAPPDATA%\Yuki\voice\tts-cache` (offline runs use their own folder). Logged: `cached_pieces` per reply, a `tts_cache` summary per conversation (counts only). A cache, never a router: nothing about what is said changes.
- **Hindi:** Gemini TTS speaks Hindi (Aura does not).
- **Cost (estimate):** $6 per 1M audio tokens (25 a second) -> ~$0.01 per 1k characters; $0.50 per 1M text tokens.
- **ElevenLabs stays an option:** `voice.json` `"tts_provider": "elevenlabs"` (or `Settings.voice_tts_provider`); the tray's "Voice id…" is its voice id. Everything below is about that option.

- **ElevenLabs Flash v2.5**; no emotion tags. The key has Text to Speech since 2026-09-25 (checked once per app run with a 1-character request).
- **The voice id is a setting the user sets:** tray → **Voice id…** (remembered in `voice.json` as `tts_voice`), or `YUKI_VOICE_ID`, or `Settings.voice_tts_voice`; empty = ElevenLabs' default (Jessica). Changing it re-runs the can-speak check, so a wrong id falls back to Deepgram with a note in the pill. Default voices retire on 2026-12-31: pick a Voice Library voice.
- **Hindi:** ElevenLabs reads Devanagari; English words stay in Latin letters (mouth prompt).

## 11. Echo handling (v3.4, `yuki/voice/echo.py`)

The mode is chosen per conversation from the Core Audio form factor of the output that **really opened** (`choose_mode`, `Settings.voice_echo`):

| Output | Mode | What happens |
|---|---|---|
| headphones (or `voice_headphone_devices`, or `voice_echo = "full"`) | `full` | the mic goes through untouched; barge-in on |
| speakers | `aec` | WebRTC AEC3 cleans every 10 ms mic frame with what Yuki played as the reference; barge-in on. Until it has shown on the stream that it removes the echo (12 dB over 0.5 s of her speech, measured; it converges in ~250 ms), it behaves like `half` |
| speakers, canceller missing or failing (`voice_echo = "half"`) | `half` | while Yuki is audible and for `voice_echo_tail_ms` (400 ms) after, the mic's audio is replaced by silence for speech recognition and the wake word; barge-in off |

- **Where:** the `EchoGuard` sits in `SharedMic.feed`, before the fan-out, so the pipeline, the wake word (after a conversation, until Yuki's last words and their tail are over), the kept audio and the levels all get the cleaned mic. Gated blocks still count as blocks (the device watch reads a still counter as a dead stream) but not towards the room's floor or "voiced".
- **Reference:** `Speaker.write` tells a `PlaybackTimeline` what it plays and when it will be heard; the mic's thread takes the reference for each frame's capture time and feeds the canceller (both calls on one thread). The devices' reported latencies are trusted by half (`LATENCY_TRUST`), so any error makes the reference early, which AEC3's delay estimator absorbs, never late, which it cannot use. The wake chime is a reference but never gates (the user goes on with their request over it; gating it cut "say something nice about" out of the first sentence, measured).
- **The canceller** loads off the critical path when a conversation on speakers starts (0.3-1.6 s; half duplex meanwhile) and is kept, adapted, for the next conversation on the same output. Voice off or wake-only never loads it.
- **Choice, measured 2026-09-26** (a simulated room: Yuki's ElevenLabs samples through a speaker nonlinearity, reverberation RT60 0.25-0.5 s, delays 40-120 ms, echo -26 to -14 dBFS, the user talking over the end): livekit 1.1.20 (WebRTC AEC3): 27-40 dB echo removed once converged, the user's own speech unchanged after Yuki stops (band gain -0.2 dB), ducked 13-17 dB while both talk, 1.7-2.6 % of one core, +19 MB RSS and ~20 idle native threads once loaded, 26 MB installed. speexdsp through `pyaec` 1.0.1: 9-22 dB, the user's speech distorted (log-spectral distance 7-13 dB against 4.8), 3.9-5.6 % of one core, 0.2 MB. `webrtc-audio-processing` and `speexdsp` have no Windows wheels for Python 3.13.
- **Offline results** (`tests/test_voice_speakers.py`, Yuki's reply saying her name twice, played into the simulated room at five alignments; the real wake listener): self-wakes without a guard 2 of 5, with half duplex or the canceller 0 of 5 (echo -4, -8, -14 dB); the user's "Yuki." after her reply heard 5 of 5 in every mode; echo removed > 20 dB over the reply. End to end (§26): no self-turn with the canceller or half duplex; 11 self-replies in 60 s without a guard.
- **What it does not cancel:** other apps' sound on the speakers (music, a video, the friends' voices in a call): only Yuki's own playback is the reference. Friends heard through speakers reach speech recognition like the user's words; the mouth's call judgement (§25) keeps it quiet on them, but a friend saying "Yuki, …" on speakers could ask her something.
- **Discord never gets Yuki's voice digitally:** Yuki plays only on the local output; there is no loopback or virtual cable (the capture endpoints are the headset mic and the M-Audio inputs only, read-only check 2026-09-26). On speakers the friends hear Yuki the way they hear any sound in the room, through the user's mic; on headphones they do not hear her at all.

## 16. Failure handling (as built)

| Failure | Behaviour |
|---|---|
| Key missing (Deepgram, Bedrock) | Preflight refuses before opening anything; the pill says which variable |
| ElevenLabs key can't speak (missing, or no Text to Speech permission) | Checked once per app run with a 1-character request; the conversation uses `voice_tts_fallback` (Deepgram, English) and the pill says why; with no fallback, voice refuses and says why |
| Speakers instead of headphones | v3.4: works (§11): echo canceller, else half duplex. `voice_require_headphones` brings back the v3.3 refusal |
| A conversation cannot start, or ends in an error (v3.4) | A short falling two-note tone on the chosen output (the same reason at most once per `voice_notice_repeat_s`) and the reason in the pill for 8 s; a tone, not words, because the failing part is often the network or a speech service |
| The chosen speaker is not in PortAudio's list (connected after the app started) | The list is re-read and the speaker opened again; if still missing, the default plays and the pill says so; the echo mode follows the device that opened |
| Mic stream dies (a device change, the PC waking) | The 3 s device watch reopens it (PortAudio's list re-read when an open fails) and retries until it opens; a dead wake listener is restarted |
| Deepgram connect slow | Audio is held until connected, then released in order |
| Fatal service error / sign-in error / network | Conversation ends; the pill shows a plain message ("can't sign in to a speech service…", "can't reach the speech services…"); the raw error is in the voice log |
| Mouth call fails or times out | Pipecat retries once on timeout; otherwise an error state for that turn; the next turn tries again. A transient Bedrock 404 ("Inference Profile ARN not found") was seen once on `global.` (§21) |
| Nobody talks | Ends after `voice_idle_s`; a running voice task holds it open up to `voice_hold_max_s`; a task waiting for the user's answer does not |
| Conversation ends while a task runs | The task is not cancelled; its result lands as a card/strip |
| Mic or speaker cannot open | Conversation ends with the error in words |
| Wake model missing | "Can't listen for 'Yuki'" in the pill, logged; the tray switch stays usable |
| Call or meeting starts | v3.4: the wake word keeps listening; a conversation in it runs in call mode (§25); `voice_wake_during_calls = False` brings back the pause |
| Voice id the account cannot use | The can-speak check fails; Deepgram's voice with a note in the pill |
| Memory lookup slow or failing | The mouth's call waits at most 60 ms and goes without; the next call gets it |
| Bedrock connection dropped by the server | httpx reconnects on the next call (one slower turn) |
| Deepgram slow to connect | Audio held; the quiet-time clock starts only once connected |

## 20. Decisions considered and rejected

(v1/v2 lists stand.) Added in v3:

- **A second wake-word model as a verifier** (the zh-en phoneme spotter re-checking the audio around a hit): misses 5 → 20 of 58, false accepts only 14 → 8 of 100.
- **Letting the mouth reject a false wake** (a `not_for_me` tool on the first turn of a woken conversation): it spoke even when it rejected, it missed most false wakes ("that tastes really yucky" got "what are you eating?"), and the note made it call tools on a plain "Yuki. Hey." Removed.
- **Eager end-of-turn on by default:** duplicated replies and a brain job (§9).
- **eot_threshold 0.6:** cut 5 of 7 paused sentences.
- **Padding the prompt for caching:** not needed (the v3 core is over 4,096 tokens) and caching saves cost, not time.
- **Running conversations in a child process** to give back Pipecat's ~110 MB after a session: the brain bridge would need an IPC protocol; not done (§21).

## 21. Open questions and risks

1. **Latency ~2.3 s** end of speech → first audio (§14); the floor is Bedrock's first token. Watch the live p50.
2. **Haiku 4.5 end-of-life** no sooner than 2026-10-16 on Bedrock, no successor listed; the id is a setting.
3. **The mouth's judgement** still slips sometimes (§5.1): repeating a result for "tell me the rest", handing over a plan the user only told it about. Live conversations will show how often.
4. **The brain can be wrong and the mouth relays it faithfully:** in one run Sonnet summed only one of two invoices over Rs 5,000 after the correction (Rs 31,500 instead of 43,900; right in the two other runs).
5. **RAM with grounding:** ~800 MB while a conversation runs (the embedder), back to ~260 MB after. `voice_grounding=False` if that is too much.
6. **Pipecat stays loaded after a session** (~110 MB above wake-only): Python cannot unload modules; a child process would.
7. **Wake word in noise:** misses rise to 13/58 at 10 dB babble and 23–27/58 at 10 dB white noise or 5 dB babble (§22).
8. **"You key" still wakes it** (3 of 102 negatives): it is the same sounds as the name.
9. **Mishearing names** (keyterms from memory's people would help); **transient Bedrock 404** on `global.` (seen once in v2).
10. **Two onnxruntime builds in one process** (sherpa-onnx's own; the Python one only when the embedder loads); Pipecat's Smart Turn no longer imports it.
11. The narrator gate, follow-up restart and cancel are covered by unit tests and one scripted run each; live use will tell.
12. **Hands (v3.2, v3.3)** are measured on a stub desktop only (rule 7). Unmeasured live: whether Chrome's document answers `ScrollPattern.SetScrollPercent` (Chromium implements it; the wheel fallback covers a no), whether Chrome's TabItems accept `SelectionItem.Select` (tested on a Win32 tab control this test owns; Invoke and the default action are the fallbacks), and the tab strip read's cost on Chrome (read ahead while the user talks, so off the reply's path). The brain and a hand can send input at the same moment (no shared lock; each is guarded to its own window).
13. **Action < 1.5 s after end of speech** is not reached (≈ 2.2-3.1 s offline in v3.3); left: Flux's end of turn (~0.5 s), Bedrock's first token (~1.0-1.4 s), the tool call's own tokens (~0.44 s; running the hand on its content block's end or on its arguments before `say_when_done` would save part), eager end-of-turn (§9).

## 22. Wake word: evaluation (2026-09-25, files only)

**Clips:** 160: v2's 131 (Aura, SAPI, Piper Hindi) plus 42 in four ElevenLabs voices (`voice_clips.py --set v3`) and 2 realistic false wakes ("He said the soup was yucky, so we just left…", "Mom, you key in the OTP here…"). 58 contain "Yuki" (alone, at the start, mid-sentence, without a pause after it, twice, in Hindi); 102 do not. Noise: v2's background talk (babble) or white noise mixed at 10 and 5 dB SNR. Script: `scripts/voice_wake_eval.py --clips <v2 clips> <v3 clips> [--babble-snr 10]`.

| Setting | Clean: misses / false accepts | Babble 10 dB | White 10 dB | Babble 5 dB | Background stream |
|---|---|---|---|---|---|
| **v2:** threshold 0.25, name only | 5/58 · **16/102** | 14 · 19 | 22 · 12 | 20 · 17 | 0 wakes |
| **v3:** threshold 0.2, name + competing variants | 5/58 · **3/102** | 13 · 2 | 23 · 1 | 27 · 1 | 0 wakes |

**Competing variants:** the spotter's keyword file lists the name and two sound-alikes (`▁ Y U CK Y`, `▁YOU ▁K E Y`, tagged `NOT_YUKI`); when a sound-alike fits the audio better, the spotter reports it and `WakeSpotter.feed` does not wake (counted as `near_misses`). What is left are "you key" (the same sounds as the name). On the confusable-heavy negative stream (every negative clip back to back, 8.2 min): 4 wakes, ≈29/h (v2: ≈80/h on its 6.7 min stream). Also tried: thresholds 0.15–0.3 and boost 3 (false accepts barely move: 13–16), the zh-en verifier and the mouth's own check (§20).

**Always-on cost** (the spotter fed at real time from memory, no device, in a process that has yuki-ui's imports): process RSS 54 MB with voice imported and off, **132 MB wake-only** (the spotter and sherpa-onnx's runtime ~62 MB, audio and queues ~15 MB); CPU 0.9–2.8% of one core in a quiet room, 2.0–5.0% with speech-level sound over four runs, including the test feeder that stands in for the device (v2 the same within noise: 1.9–2.4% / 3.0–5.0%). No Pipecat, Deepgram, Anthropic, onnxruntime or embedder is loaded until a wake.

**During calls** (v3.4) the listener keeps listening (`voice_wake_during_calls`); a conversation started or running in a call is in call mode (§25). Before v3.4 it stopped and the mic closed, which is why "Yuki" did nothing through the 25 Sept Discord call.

**Each sound episode is decoded afresh** (v3.4): when the sound gate closes after a second of quiet the spotter's stream is reset, so the next episode starts clean with its pre-roll. Without it, seconds of other speech left in the stream cost the name that came right after (Yuki's residual echo in the simulated room: the user's "Yuki." heard at 2 of 5 alignments; with it 5 of 5). `scripts/voice_wake_eval.py` feeds the spotter directly, so the §22 figures are unchanged.

**What the spotter gets** (read-only device query, 2026-09-26): the tray's microphone "Line 1/2 (4- M-Audio AIR 192 4)" is a 2-channel 48 kHz interface input, opened in WASAPI shared mode with Windows converting to 16 kHz mono float; the louder channel of each block is kept. The live logs show its level on speakers: floor -25 to -32 dBFS with 90 % of blocks above -42 dBFS (the room's sound from the speakers reaching the mic) and a block at full scale (0.0 dBFS RMS), against a -48 dBFS floor and -5 to -11 dBFS peaks on headphones. The levels event now also logs the peak, clipped blocks and which channel was used, so the next live run says whether the input clips; the gain itself is the interface's knob, not Yuki's. The name was still heard all 5 times at 18:20.

## 25. Call mode (v3.4)

**v3.10:** a call exists only with screen evidence (memory's `callevidence`: a joined call seen on the screen during the microphone hold; a microphone alone is a hint). Fresh evidence: the strict `CALL_LAYER` (speak only when called by name or plainly still talking with Yuki; stay_quiet alone, never a word about whom the words were for). Stale evidence: `CALL_LAYER_UNSURE` (plain instructions are for Yuki with no question; only ambiguous words get "Was that for me?"). Both notes are private and never to be said.

A conversation is in call mode while memory's `call_status` reports a call (`VoiceSession.on_call_status`; a call that starts or ends during a conversation switches it at once, `Conversation.set_call`).

- **Who was addressed is the mouth's judgement**, never code's: a call layer (`mouth.CALL_LAYER`, a system block present only in call mode, so a conversation without a call sends exactly what v3.3 sent) says the microphone hears everything the user says, to Yuki and to the people on the call; before every reply decide who the latest words were for; for Yuki = the name, or plainly still talking with her (answering her, reacting to what she just did, adding to what they just asked); everything else (chat, banter, game talk, questions to friends, talk about her) is for the call: `stay_quiet` alone, no words; when unsure, for the call ("if it was for you, they will say your name"); when for her, answer as briefly as possible. Worked good/bad examples, no word lists. Every request's volatile block carries the call line. `stay_quiet`'s description keeps "never when the user has just spoken to you" with one exception while the call note is there (a rewording that dropped "Only" made the mouth stay quiet on a direct request outside a call, measured once; restored).
- **It ends sooner:** (v3.16: never while their newest turn has no audible answer, a held hand waits, an outcome is owed, or the mic hears them talking; stalls do not count; it ends with the end cue) `voice_call_idle_s` (10 s) after the last exchange with Yuki (she spoke, acted or handed over, `TurnObserver.last_exchange`); talk to the call does not count, so the rest of the call is neither streamed nor judged. A sentence the user is still saying gets 4 s more (`CALL_SPEECH_GRACE_S`), and a reply that just ended is waited on for 1 s while its tool call starts (`CALL_TOOL_START_S`; measured: without it a run ended 0.4 s before the "turn it up" hand it had decided on). A running task still holds it open like any conversation.
- **Nothing of the call is learned:** (v3.5: every turn is now written to conversation memory with `addressed` = yuki / others, and memory never extracts the "others" ones; before v3.5) a call-mode user turn Yuki took no part in (`stay_quiet`, or cut short by the next words) was not written to conversation memory (the call memory has the user's side, with their consent, on its own terms), and the thinker is never handed those words as what the user said (`pipeline.quiet_answered`). The voice log's turn event says `call_mode` and `addressed` (yuki / others / unanswered); the bridge logs `quiet` with `addressed: others`. Since report 77b memory gets "unanswered" for a turn cut off by the next words (nobody judged it; memory's extractor does, from the words) and "others" only for the talker's stay_quiet; the last-hour view also keeps words said to Yuki that got no spoken reply (an action alone, the first part of a request cut off by its own next words).
- **Measured end to end** (`voice_session_offline.py call|call2`, real Flux and Haiku, Discord call, headphones and speakers with the canceller): "Yuki, pause the music" acted on in 6 of 6 runs (the media key, "Paused."); every line to the friends got `stay_quiet` and no words: "Bro, did you see that clutch?" 4/4, "No way, he got all three of them, that's insane." 3/3, "What are we doing after this?" 3/3, "Can you guys hear me?" 1/1, "Haha okay okay, let's queue again." 1/1; "Yuki, turn it up a bit" mid-conversation (heard as "If you turn it up a bit") acted on 2/2; each conversation ended ~10 s after the last exchange, and later talk was never streamed.
